# FC1 64-token FP32 batching: read-only assessment

No implementation, compilation or new timing. The actual source-bound N3U TP W4A4 T16384 SourceCounters record has9892 epilogue-body samples and9913 gather-body samples. The epilogue accumulator-full wait accounts1907 long-scoreboard samples; other epilogue work accounts3019. SF cp.async plus its completion account1986 of2934 MIO samples; Gather4 itself accounts227. This does not isolate an epilogue-fence throughput bottleneck. PC sample shares are not wall-time shares.

Targeted Markdown searches of prior fc1-gather-20261028 and scripts found no direct experiment batching two32-token FP32 FC1 slabs. Prior paired-transpose work batches the two channel halves within ONE32-token slab; the two-epilogue-WG audit partitions32-token slabs between extra groups. Neither is this proposed64-token batching. The absence claim is bounded to those searches.

Current _blockscaled_transpose16x32 follows a32-row x32-column scratch rectangle per warp. Its fragments select row offsets0/16 for the two channel halves, so increasing fragments to4 without changing the mapping writes outside a warp's32-row ownership. A64-token batch needs an explicit two-slab column index, keeping each slab's row halves at0/16 and token columns separated by32. Each lane then owns two independent tokens and separate SF16/SF32 maxima and stores. Per-token alpha lookup also has two independent token indices.

The current32-token ReLU2 body holds32 FP32 input/output values per thread; batching doubles those logical values before accounting for transpose work/results, metadata and quantization. The epilogue's248-register limit and64512-register CTA pool are unchanged. Actual codegen and zero-local-memory evidence would be necessary; assigned register indices alone do not establish available liveness.

Most importantly, run_overlapping_fc1 releases the accumulator after the shape-derived protected32-column slabs. A batch must not hide a release boundary. Simply releasing after both slabs is safe but can delay the next MMA for a further32-token transpose/quantization chunk. Preserving earlier release requires two completion points or splitting batches at the boundary; this introduces exactly the control/layout complexity the user asks to justify. The existing scale footprint can imply odd protected slab counts, so a universal64-token policy cannot assume the boundary is always even.

Conclusion: do not implement based solely on aggregate epilogue activity. The current mixed gather/epilogue evidence does not establish that saved fences outweigh extra register liveness and delayed accumulator release. No shape-specific fallback or new tuning axis is proposed. The separately observed SF transport pressure has a documented canonical-layout obstacle to wider direct cp.async/TMA; do not silently reopen that rejected redesign either.
