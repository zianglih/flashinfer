# W4 whole-M padding: zero-store alternative closed

Read-only audit at retained `2b8eb9d8f72ceda3952fbb05054fee97173fc9c7`, W4 kernel `5e61d04544524410b273b8e49ee2b8f6d9e20266c22346aba06ab3743c2c4e1d`. **Closed without prototype or GPU work:** the defined-zero alternative avoids the uninitialized-TMEM concern, but needs a new private M handoff and branch with no demonstrated latency mechanism. The independently owned output-ring experiment is unchanged.

## Existing ownership and bounds

The split wrapper constructs A with exact `(m,k,experts)` (`moe_w4a16_kernel.py:860`) and block-scaled SFA from that shape. Each public tactic has 128 M rows per CTA; M256 is a two-CTA MMA. The scheduler already publishes the CTA M index in its four-word metadata record. Transform warps copy this record into registers before releasing its slot, so the caller can calculate `work_tile.cta_coord_m * self.cta_tile_shape_mnk[0] >= mA_mkl.shape[0]` without new metadata or global loads. Both static and CLC scheduling use that existing coordinate. The coarse `self.m_cluster_aligned` flag is already available but does not identify which CTA is padded.

The shared `_transform_tile` helper receives only consumed K and transform-group index, not M or the work tile (`:703–834`, caller `:2121`). Both transform groups cover all CTA M rows and divide K. The saved actual-CuTe layout proof checks 5,120 thread/group records: for stage K256, each thread owns one row and 128 K values; the groups own K[0,128) and K[128,256). Gated row64-to-row16 remapping stays within a CTA. The public gate/up32- or128-row pairs fit its128 rows; see `w4-physical-work-2b8.md`. Generic private M64 construction is outside that proof and already fails the retained transform partition in the saved probes.

For public whole-invalid CTAs, the CTA start is 128-aligned. If it is at or beyond logical M, it is also at or beyond `ceil(M/128)*128`, the padded SF extent (`convert_sf_to_mma_layout`, `cute_dsl/utils.py:367`; SF atom `(32,4)` in CUTLASS `blockscaled_layout.py`). Thus this is beyond the final SF tile, not an assumption that an in-bounds padded SF byte is zero. Raw TMA zero-fill and SFA zero-fill produce defined zero decoded BF16. CUDA13.2's [TMA boundary specification](https://docs.nvidia.com/cuda/archive/13.2.2/parallel-thread-execution/index.html#tensor-tiled-mode-oob-access) distinguishes zero fill from OOB-NaN fill; no fill-mode change is proposed. Partially live CTAs remain unchanged.

## Why the current K-tail branch cannot be reused

The retained `transform_valid` means **MMA will not consume this K group**, so its false path skips both decode and TMEM writes. It is possible only at the final K stage. It advances the raw consumer once without querying the next stage (`:810–812`). The live path queries the next raw stage after its final raw fragment load (`:783–790`).

An M-invalid CTA persists across many K stages, while group2 MMA still reads its A rows. Folding M-invalid into `transform_valid` would both leave TMEM unwritten and retain a stale cached raw-ready token across stages. Even if stores were restored, the current false branch's missing next-stage query remains incorrect for this use. Passing consumed K=0 is also invalid: it removes required decoded-stage publications entirely.

A correct alternative would fill the existing `tArA_transform` register fragment with zero, keep all currently live-K TMEM stores, and retain raw wait, decoded acquire, raw release, decoded commit/advance and terminal tails. It must separately maintain the next-stage raw query. It requires at least one explicit private M-valid handoff plus a zero/decode value branch; the two shared MegaMoE callers also need an explicit contract. Deriving M from the SMEM fragment alone is impossible: its layout is stage-local and has no logical global M bound. A per-tile runtime attribute or duplicate caller-side transform loop is more complex, not a cleaner alternative.

## Work removed versus work retained

For one whole-invalid public CTA at stage K256, the upper-bound dynamic work avoided is the shared-memory reads of16KiB packed A plus2KiB SF and conversion of32,768 values. Each transform thread owns128 values, so its direct16-value decoder runs eight times (each with one scale PRMT/conversion, eight FP4-pair conversions and eight BF16-pair multiplies, plus extraction). These are source/PTX operations, **not newly measured SASS savings**. Zero materialization still feeds the existing64KiB total BF16 TMEM writes per CTA/stage; all pipeline barriers, TMA transactions/expected-byte bookkeeping and group2 MMA remain. Allocation, occupancy and raw-weight DRAM traffic do not improve: the removed source loads read SMEM, and OOB TMA does not fetch valid weights.

The valid peer CTA still performs the full transform and participates in the same two-CTA decoded publication. No saved profile establishes that the padded CTA's decode, rather than the valid peer's weight arrival/decode, limits progress. Less work on the invalid SM could reduce local instruction/power demand, but that is not a measured E2E mechanism. Adding control/interface complexity for this speculative benefit fails the current retention criterion.
