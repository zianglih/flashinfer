# Swap FC1 unified completion: source-only closure

**Do not prototype from the present evidence.** A one-CTA merge is expressible without a public argument, but repeats the previously rejected topology-dependent relay bypass and additionally serializes SFA copies behind gathered-input completion. A uniform, SF-only relay into operand-full avoids that policy split but retains the relay and has the same serialization cost. No source, compiler, GPU, cache, or timing operation was performed.

Audited canonical HEAD `c1ac8ce7341039db65195b99445fcdeb193cf226`, clean; swap SHA `482b636a1714486e2ffb34c8ae005da3cef26f25f0ce034ba1eb59c6198d6276`. The retained 2b8 TP profile uses these exact swap bytes. The separate SF/payload slot-interleave experiment and its evidence are untouched.

## Current ownership

All locations below refer to `flashinfer/flashinfer/fused_moe/cute_dsl/blackwell/moe_swap_ab_kernel.py`.

| Resource | Current owner and dependency |
|---|---|
| Operand-full | Weight warp announces weight/SFA bytes; one expected arrival, transaction count excludes gathered B/SFB (`2544–2579`, `2673–2685`). |
| Operand-empty | Weight and all gather issuers independently acquire this common reuse phase. MMA releases it only after both operands have been consumed. Sharing this lifetime does not make the two full-readiness events simultaneous. |
| Gather-local | One arrival announces all local Gather4 payload bytes; `R=min(route_tile,128)` SF participants each attach their prior copies with `cp.async.mbarrier.arrive.noinc`. Count is `1+R`, including participants whose rows are padded (`2731–2742`, `3504–3576`). |
| Gather-ready | Activation warp acquires local completion, applies the async/shared proxy fence, then publishes one arrival per CTA to the leader (`3016–3053`). Group2 uses the explicit cluster release/acquire helpers (`118–168`). |
| MMA | Acquire weight-full, issue SFA S2T, acquire gather-ready, issue SFB S2T and MMA (`3202–3247`). These waits protect different inputs. |

The activation warp also owns startup PDL acquisition/publication (`2756–2779`); removing its per-tile relay loop does not remove that startup responsibility. CLC counts it as a metadata consumer (`2705`), so bypassing the loop requires a matching consumer-count change. Ring phase advancement across K/work tiles, terminal joins and the sole operand producer tail must remain intact.

## Hardware feasibility and boundary

PTX9.2 restricts `cp.async.mbarrier.arrive` to a barrier in the executing CTA's shared-memory window; a peer CTA cannot simply attach its SF completion to the leader's barrier. `.noinc` requires the asynchronous arrival to be included in initialization. A successful acquire observes tracked copies, but the generic-to-async proxy fence before SFB `tcgen05.cp` remains necessary. See [cp.async completion](https://docs.nvidia.com/cuda/archive/13.2.0/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-cp-async-mbarrier-arrive), [mbarrier waits](https://docs.nvidia.com/cuda/archive/13.2.0/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-mbarrier-test-wait-mbarrier-try-wait), and [tcgen05 shared-memory ordering](https://docs.nvidia.com/cuda/archive/13.2.2/parallel-thread-execution/index.html#tcgen05-memory-consistency-model-smem-access).

For one CTA, a possible contract is full count `1+R`, with the weight warp announcing weight/SFA plus Gather4 bytes. Both Gather4 transaction completions and SF noinc arrivals target operand-full. The reserved weight arrival prevents premature phase completion even if Gather4 finishes first: the permitted signed transaction counter accommodates completion-before-expect, then atomic expect/arrive accounts for the outstanding bytes. This is analogous to independently issued regular B TMA today; it does not require a producer rendezvous. [Counter limits](https://docs.nvidia.com/cuda/archive/13.2.0/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-mbarrier-contents). The independent [ordering audit](gather-full-merge-ordering.md) reaches the same feasibility and closure boundary.

That construction still changes at least six coupled source areas: full arrival/byte accounting; gather completion pointers and local announcement; relay role/CLC consumer count; MMA wait/proxy placement; conditional barrier initialization/storage; and matching storage/planner accounting if dead arrays are removed. Keeping unused storage avoids a planner change but repeats the previous unfinished dead-storage boundary. This is not a one-line deletion or a new independently established simplification.

For both topologies uniformly, Gather4 could complete directly into operand-full while an SF-only local barrier feeds a relay arrival into that same full barrier. Full count would cover the weight announcer plus one SF relay arrival per CTA; SF-only local count would be `R`. Group2 still needs leader-addressed Gather4 completion and cluster publication/acquisition, not the present ordinary CTA-scoped operand wait alone. This can eliminate gather-ready storage and the second wait, **not** the SF relay. It remains a different synchronization graph needing its own proof. Moving SFA publication to a producer to recover overlap would additionally change TMEM ownership/readiness, or add another queue/slot/synchronization mechanism; it is outside this small lead.

## Native cost and exact history

The current N3U TP8 T16384 W4A4 FC1 is one CTA, M128/N256/K256, four operand stages. Its actual cubin is `db9cf0157a08bef023af8c67b2830bd52b9eeb13d73a3e97e6b7538234d47551`. In [the saved SASS](../profiling/n3u-tp-w4a4-16k/retained-2b8/fc1-pc/loaded-codegen/64743/fc1.sass), weight-ready TRY is `0x2540`, four SFA `UTCCP` instructions are `0x25c0/25f0/2600/2610`, and gather-ready TRY is `0x2620`. Merging readiness delays those four useful copies until B/SFB is ready. The [current PC report](../profiling/n3u-tp-w4a4-16k/retained-2b8/PC_RESULTS.md) records 76 weight-ready, 1,280 gather-ready and 789 relay long-scoreboard observations. These are sampled dependency locations, not removable relay latency. The unchanged SF issue/completion path itself accounts for 1,518 MIO observations; merging barriers does not remove those copies or their noinc completion instruction.

The precise prior is [gather-direct-wait-screen/RESULTS.md](../../flashinfer-w4a4-split-dynamic-n/fc1-gather-20261028/optimization-next-20261029/gather-direct-wait-screen/RESULTS.md), candidate `c5373aa1` on `b52e4e09`; its [patch](../../flashinfer-w4a4-split-dynamic-n/fc1-gather-20261028/optimization-next-20261029/gather-direct-wait-b52/candidate.patch) made MMA wait on local completion in one CTA and retained the two-CTA relay. It preserved two MMA waits and SFA overlap, so **it did not test a unified operand barrier**. Nevertheless, it already removed 24–46 FC1 non-NOP instructions and 6–14 branch/control sites, passed 41 exact cases/80 captures, then measured only **+0.0062% across 20 affected cells** (+0.0398% across all24). It was explicitly rejected for neutral benefit plus `gather_relay`/topology complexity. Tight adverse cells included N3U TP16K W4A4 −0.430% and N3U EP8 MXFP4x8 −0.408%. No silent reopening under “direct completion.”

The [universal SFA-copy order screen](../../flashinfer-w4a4-split-dynamic-n/fc1-gather-20261028/full-20261029/sfa-overlap/universal-copy-order/RESULTS.md) was itself near-neutral (+0.098% affected36; prefill +0.191%, noisy large cells); it supports the independent-readiness structure, not a quantified penalty for merging it. Targeted current/old ledgers, relay-scope, direct-wait patches and gather-pipeline audits found no exact merged-full-barrier timing trial. That negative search is bounded, not a claim that the idea has never been tried elsewhere.

## Reference boundary and decision

W4 Gather4 completes directly into its **B** pipeline (`moe_w4a16_kernel.py:1234–1248,2815–2857`), but BF16 B has no activation-SF cp.async stream. It still has independent transformed-A readiness. Rubin's TMA path merges payload/weight transaction completion (`rubin/blockscaled_contiguous_gather_grouped_gemm_swiglu_fusion.py:1503–1525`), while SF uses separate copy/transform pipelines (`1411–1444`). Its cp.async path explicitly retains a two-CTA relay (`1448–1487`). Neither is a drop-in mixed-SF completion proof for swap.

The possible extra saving beyond the rejected bypass is one readiness check/branch/slow path, purchased by delaying useful SFA issue and moving the proxy fence onto MMA. The all-topology variant avoids the rejected one-/two-CTA policy but still loses that overlap and does not remove the SF relay or transport pressure. Without evidence separating unnecessary handoff delay from real B/SFB availability, instruction count alone does not justify either implementation. Close this lead at source/native audit; no prototype, tuning rule, or retention claim.
