# SF address rematerialization inside the existing copy

Read-only assessment against retained `c1ac8ce7` (swap source `482b636a`), rejected R1 `86836355`, and R2 `377f0404`. No source, compiler, GPU, quota, or cache changes.

The mechanism is distinct from R2 and can stay inside the existing `_copy_gather_sf` primitive, but it is an address-lifetime tradeoff, not established work removal or a spill fix. The smallest private contract adds **Int32 row and constexpr row stride**; its existing source-pointer operand can already carry `sf_base + channel/sf_vec`. No separate channel argument, new helper, public restriction, state machine, or barrier is necessary. The existing R2 compact row cache would still be required.

Inside the existing side-effecting assembly, signed-widen the row and form the final address with `cvt.s64.s32` plus `mad.lo.s64` using the constexpr stride, then retain the exact four-byte predicated `cp.async` and ignore-source behavior. This preserves `Int64(row) * stride + base + channel` modulo 64-bit address arithmetic. Do not substitute an unconditional `mad.wide.s32`: current `can_implement` has no upper-K/stride limit. PTX permits 64-bit low-product MAD, whereas wide MAD has 16/32-bit multiplicands. [PTX integer MAD](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#integer-arithmetic-instructions-mad)

The frontend cannot extract arithmetic from this opaque assembly template as it did with R2's pure CuTe expression. This does **not** constrain PTXAS register allocation or scheduling, and a scoped PTX temporary is not a native lifetime guarantee. The CUDA guide describes side-effect/memory protection during PTX generation and separately notes that the frontend does not parse the assembly. [CUDA 13.2 inline assembly](https://docs.nvidia.com/cuda/archive/13.2.0/inline-ptx-assembly/index.html#incorrect-optimization)

Current source/native evidence:

- The primitive is at `flashinfer/flashinfer/fused_moe/cute_dsl/blackwell/moe_swap_ab_kernel.py:95`; source-row widening/caching and per-stage address construction are at `:3478` and `:3523`; unchanged copy predicates/publication follow at `:3535`. `can_implement` ends at `:2061` with alignment/capacity constraints, not a stride cap.
- Failed wide MXFP8 N256/K8/G2 PTX computes four `mul.wide.u32 ...,32` before the K loop (lines 3880/3887/3894/3901, loop 3922). SASS retains offset pairs R60/R58/R56/R54, produced by four `IMAD.WIDE.U32` at `c430/c480/c4c0/c520`. Every stage forms all four final addresses with eight `IADD3/IADD3.X` at `d460`–`d4e0`, before SF copies `d540/dda0/de20/deb0` separated by substantial Gather4 work.
- Compact row storage could save **four persistent 32-bit words** in that geometry (eight offset words to four row words). Separately, computing each final address at its copy might shorten the four simultaneous full-address pairs. Neither saving is measured. Up to 64 Gather4 row IDs and coalescing's extra row predicates/map loads remain; the 64-byte spill cannot be attributed entirely to SF offsets.
- Four K stages would recompute **16 row products instead of four**, or twelve extra product evaluations per work tile. For B row blocks, W words/row and G lanes/row, products change from B*G once to B*W per stage. MAD can absorb an address addition, so this is not a defensible fixed increase in native instruction count: the current eight adds/stage may lower differently under rematerialization. Both operation count and address lifetime need actual native comparison.

The memory-side benefit is conditional. For distinct rows that do not cross sector boundaries, V live rows and R valid four-byte words/stage give request counts `V*R` versus `V*ceil(R/G)`. This is not universally G-fold: R=1 has no gain; generic four-byte-aligned rows can cross sectors; repeated/adjacent routed rows may already coalesce. Global byte addresses and unique sectors are unchanged, so no DRAM-byte saving follows. Zero-fill copies and shared destination/publication requirements remain; group-2 replicates full-N SFB in both CTAs. Compact persistent SF state is B*G words versus production's 2*B: G2 restores the production count, G4 still adds 2*B.

Bounded history search found no exact address-arithmetic-inside-copy trial. R2 only moved a pure expression and produced byte-identical spilling PTX/cubin. The older `scripts/perf_round_20261027/sf-source-address` experiment removed an inactive-row selector in a prepared-layout copy; it did not rematerialize routed row products inside assembly. Cache-hint, copy-width, and lane-mapping trials are separate.

Verdict: a small native stress probe could answer this distinct compiler question if separately authorized; inspection cannot establish that four saved persistent words remove spills or that added products beat the sector-request benefit. It does not justify a qualification matrix or timing yet. Preserve exact 64-bit arithmetic, all masks/arrivals, and normal compiler/resource limits; abandon if native allocation reconstructs the same state or spills persist.
