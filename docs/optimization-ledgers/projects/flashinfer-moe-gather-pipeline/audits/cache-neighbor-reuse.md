# Existing metadata cannot replace the two neighbor queries

Read-only audit of the current project source; no production edits or GPU work. Source hashes and explicit counterexamples are in `cache-neighbor-reuse.json`.

The retained helper (`moe_swap_ab_kernel.py:2507–2517`) selects normal weight/SFA priority whenever another routed tile belongs to the expert, and evict-first for a single-tile expert. Its two bounded expert-ID loads occur once per work item, outside the K loop (`:2870–2880`). No new policy is recommended.

- **Current `mn_limit` does not identify expert extent.** All three routing writers use `min(tile_end, expert_end)` (`RoutingKernel.cuh:474–484`, `:781–791`, `:1163–1173`). A full tile is indistinguishable from either a singleton or part of a larger expert. The CLC metadata contains only tile, expert, and valid rows (`moe_swap_ab_kernel.py:2798–2812`); the valid count is already clamped.
- **One neighbor is not sufficient either.** With route size16, counts `[16,16,16]` and `[16,32,0]` give the same current route1/expert1/limit32/total3 tiles/total48 rows and the same previous expert0, but only the latter has reuse. Counts `[16,16,16]` and `[0,32,16]` give the same current metadata and next expert2, but only the latter has reuse. The JSON checks both counterexamples. Boundary-special-casing or partial-tile checks cannot eliminate the general case.
- **No authoritative count is already available to GEMM.** `moe_utils.py:759–774` allocates internal expert counts only for large routing paths, and `:808–815` returns six routing tensors without those counts. The newer routing count-output pointer is not wired by this MoE API. Adding it would change the routing/interface contract, which is outside this simplification.
- **Traversal does not imply adjacent-route ownership.** Static work advances by grid stride; CLC cancellation can return another route. A saved prior expert or a final-route test cannot identify the current expert's other consumers or their execution order. Moving the hint to the unused fourth CLC metadata slot only relocates the reads and burdens the scheduler; it is not an equivalent removal.

The older project already reached the same conclusion in `optimization-20261027/prepare/routing-neighbor-load-audit.md`. Its initial `mn_limit` prototype was superseded before measurement (`optimization-20261027/cache/REUSE_POLICY.md`). Targeted searches of the old optimization, gather, and script Markdown ledgers found no measured next-only/previous-only variant. The separately rejected first-hint reuse variant added state/branching and did not justify that cost.

A next-only or previous-only policy would be shorter, but would deliberately stream one tile of every multi-tile expert. It is not an exact simplification, and physical route order does not guarantee that the chosen boundary tile is the final weight user. In existing frozen 16K histograms, that changes 255/632 route tiles (40.35%) for V3 TP MXFP8 and 512/1667 (30.71%) for N3U TP W4A4. These are classification counts, not predicted timing effects. The fresh constant-policy losses make weakening the reuse policy without a stronger mechanism unpersuasive.

**Decision:** close this lead read-only. Keep the existing two bounded loads and the simple route-aware policy; introduce no packed flags, new metadata, public argument, alternate CLC policy, or extra control state.
