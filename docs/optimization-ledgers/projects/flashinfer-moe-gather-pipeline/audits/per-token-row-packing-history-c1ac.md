# Per-token quantizer: simultaneous row packing remains untested

**Bounded conclusion:** no implemented/tested simultaneous independent-row CTA was found in the handoff/width/two-blocks/paired-width/warp-reduce ledgers. The exact idea appears as an explicitly unestablished direction in old `fc1-gather-20261028/optimization-next-20261029/per-token-handoff-475/RESULTS.md:33`. This is distinct from changing one row's CTA width64→32. No prototype or GPU work was performed; wait for actual instruction/PC attribution before proposing a design.

**History boundaries.** `scripts/row_grid_quantizer_20261026/README.md` says “multi-row CTA reuse,” but implements sequential grid-stride rows with one CTA-wide reduction buffer, not simultaneous rows. The later retained `per-token-warp-reduce` merely bypasses shared reduction/reuse barriers when the existing CTA has one warp. The rejected paired-width policy still uses one row per CTA: N3U TP32 lost2.231%, and its same-GPU follow-up lost2.109%/1.425% at T32/T64. K640 intermediate quantization rose15.568→18.056 and19.632→22.280µs; routing holes and the doubled CTA-grid cap remain relevant boundaries.

The old `per-token-two-blocks/micro-evidence/codegen/resources.json` does show that K640's width change can fit: the32-thread version has63 registers, zero stack/LDL/STL and zero BAR sites;64 threads has64 registers, zero stack/LDL/STL and two BAR sites. Both use precise MSE256/error-fast math. These are diagnostic captures with `--keep-cubin` and `no_cache=True`, not current loaded images. Wider K cases in the separate register-width diagnostic spilled and regressed. Thus neither “packing inevitably spills” nor “one warp universally wins” is supported.

**Current source.** `flashinfer/flashinfer/quantization/kernels/nvfp4_quantize.py:858–883,935–946,1029–1034,1064–1092,1219–1223,1269–1296,3413–3418` jointly define row width, persistent grid, launch bounds, row validity and reductions. K640 has40 real16-value blocks;64 threads hold one block each, including24 harmless repeated last-block loads. A32-thread row holds two blocks per lane: the same64 total block loads, but twice the per-lane input fragment. Its invalid rows also need two SF-clear iterations instead of one. The register-resident threshold becomes K≤4096 if every row is forced to one warp; current wider rows can remain register-resident much farther. A universal warp-row rewrite would change that established policy, not just CTA packing.

`flashinfer/flashinfer/cute_dsl/fp4_common.py:1356–1391` already provides both ingredients:

- `warp_reduce` is warp-local. Independent warp rows could reuse it with warp-relative lane/row indexing; no shared reduction buffer, arrival state or per-row CTA barrier is intrinsically needed. Validity and loop control must remain uniform within each participating warp, with the existing PDL wait/ancestor publication/startup signal and SF-padding semantics preserved.
- `block_reduce` already indexes a `(rows, warps_per_row)` buffer using physical warp ID, but executes a **CTA-wide barrier**. Packing unchanged64-thread rows therefore does not remove cross-warp reduction, and different rows cannot independently skip the helper when they hit holes or the final partial batch. Uniform batch participation plus the existing scratch-reuse barrier would be necessary; the current validity branch cannot simply be copied around the grouped helper.

**Resource/launch boundary.** Current launch bounds and grid cap target1024 threads/SM:16×64-thread CTAs, or32×32-thread CTAs. Packing four warp rows into a128-thread CTA would target8 CTAs/SM, still32 warps; it does not automatically raise the residency budget or relax the roughly64-register/thread budget. It may change CTA scheduling/loop overhead, but does not remove per-lane quantization arithmetic or the doubled live input fragment. Grouping unchanged two-warp rows keeps only16 row groups per1024 resident threads and retains the barriers.

The fresh retained profile's aggregate metrics (`profiling/n3u-tp-per-token-16k/retained-c1ac/metrics-summary.json`) report 61 registers, 64 threads, LOCAL0 and 16-CTA occupancy, with grid 2368; 360,448 live rows within 426,752 processed rows (66,304 holes). Issue activity is 78.74%, barrier 4.72%, DRAM 18.31%, long scoreboard 24.44%, and math throttle 5.81%. Barrier removal alone is therefore a limited signal, while broad width tuning already has negative evidence. These aggregates do not establish that row packing attacks the dominant instructions; actual PC attribution remains separate. This read-only audit is closed without a prototype, new row policy, shape exception or performance claim.
