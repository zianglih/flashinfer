# Whole-M zero-fill: shared MegaMoE handoff and readiness

Read-only on retained `2b8eb9d8`. No source edits, GPU work, or new numerical claim. This supplements `w4-oob-m-zero-fill.md`; the independent owner supplies actual selected-winner affectedness.

- **The M bound is already available in the caller.** `MoEFusedFc12SchedulerParams` selects swap-AB and converts its internal token/channel axes back on output. `_decode_inside_expert` computes `cta_intermediate_or_hidden_block_idx = cluster_channel_idx * params.cluster_shape_mn[1] + cta_id_in_cluster[1]`, and publishes exactly that as `work.tile_m_idx` (`fc1_fc2_fuse_sched.py:883–904`). This is a CTA-local channel index, not a logical MMA tile index. The inherited physical CTA width is `self.cta_tile_shape_mnk[0]` (`megamoe_kernel.py:747`). Thus a caller-side live-M predicate is `work.tile_m_idx * self.cta_tile_shape_mnk[0] < self.intermediate_gateup` for FC1 and `< self.hidden` for FC2. Both bounds are constructor constants (`:237–242`); both calls already branch on the existing phase (`:1596–1615`). No extra scheduler record, GMEM read, or runtime attribute is needed.
- **Do not divide the index for this predicate.** `_weight_task` divides `work.tile_m_idx` by `cute.size(mma.thr_id.shape)` (`:943`) only to index the logical MMA-sized source tile; its `mma.get_slice(cta_v)` separately selects the physical CTA slice. Using that divided index for M validity would incorrectly declare the padded peer of a two-CTA tile live.
- **One private handoff remains necessary.** Shared `_transform_tile` presently receives consumed K and transform-group index, but no global M coordinate/bound. Both Mega call sites would need to pass an explicit derived predicate. Their padded consumed-K argument must remain unchanged: Mega issues every padded final-stage MMA column (`:1413–1450`). This is independent of whether the CTA has live M outputs.
- **Group2 readiness still includes the valid peer.** `transform_pipe` has `32 * num_transform_warps * cta_v_size` thread producers (`:1169`), with eight transform warps. Group2 therefore requires 512 producer arrivals across the two CTAs; only its leader consumes the stage before full MMA issue (`:1421–1449`). An invalid-M CTA that replaces load/decode with zeros must still write every consumed decoded TMEM column, fence, and contribute all arrivals. The live peer performs full transform and remains a lower bound on readiness. Less work on the invalid SM could reduce local issue/power pressure, but this source trace does not establish an exposed end-to-end wait.
- **Group1 is a distinct boundary, not automatically a peer stall.** With `cta_v_size == 1`, the transform producer count is 256 and each MMA consumes its own CTA stage. Even if the cluster has two CTAs, the above 512-arrival group2 argument does not apply. The zero-fill idea may save independent invalid-CTA instructions, but raw-TMA/multicast/scheduler and output completion contracts remain; no latency benefit has been measured. Keep this distinction in interpreting the two selected group1 cells.
- **All phase work stays.** A false M predicate can occur on every K stage, unlike the retained wholly-unused-K branch which is final-stage only. A zero path must preserve raw wait/acquire/advance/next peek/release, decoded acquire/store/fence/commit/advance and terminal drains. It cannot reuse `transform_valid=False`, consumed K zero, or the K-tail no-next-peek path. Existing decoded destinations can be zero-filled without changing layout, but that is an additional value branch/interface contract, not free removal of the transform role.

The minimal caller expression is available and general, including phase-specific static bounds. The group2 critical-path concern from the previous closure still holds; group1 should be evaluated separately if a prototype is ever authorized. This audit does not reopen the proposal by itself.
