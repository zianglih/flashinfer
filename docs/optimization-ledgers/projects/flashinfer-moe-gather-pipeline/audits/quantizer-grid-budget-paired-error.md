# Per-token quantizer grid budget: bounded history/API check

The current source uses `min(padded_M, num_sms * (1024 // threads))` independently of actual compiled registers (`nvfp4_quantize.py:3413–3418`). The compiler minimum-residency hint uses the same budget at 946. K640 therefore launches 2368 CTAs on 148 SMs even when the paired-error binary's pilot capacity rises 16→20 CTAs/SM; the wide K3 rows launch 1184. These are total-grid averages, not per-SM residency caps. Actual placement and PDL concurrency were not traced in the timing harness.

The directly matching historical experiment is oldproject `scripts/row_grid_quantizer_20261026/README.md`: it retained this 1024-thread bounded grid instead of one CTA per allocation row. Its source-paired prefill ratios improve approximately 5–15.5% in the three-model bounded screen. It did **not** compare 1024 against higher budgets or a driver-resource-derived grid. The bounded checks of both CLOSED_LEADS indices and per-token handoff/warp-reduce/two-blocks/paired-width ledgers found no matching tested dynamic-resource query or higher-budget sweep. Width trials change both work/liveness and CTA counts; they do not isolate this question. This is a bounded absence finding, not a claim about every archived export.

There is no existing quantizer helper that returns occupancy or a loaded CUDA function handle. `_get_compiled_kernel_nvfp4_per_token` returns the generic persistent-cache callable; `JitSpecCuteDsl._load_from_disk` (`cute_dsl_core.py:262–266`) returns an exported TVM-FFI function. The existing repository `_grid_fits` example (`comm/tp_moe_finalize_rmsnorm.py:1859–1901`) loads a kept cubin into a separate driver module for a query. The qualification harness similarly loads a diagnostic library. Neither is a drop-in call on the cached quantizer callable.

A resource-derived grid is internally possible without a public knob, but would need cached native metadata/handle plumbing that works on both compile misses and disk-cache hits, plus device/dynamic-shared-memory-aware lifetime handling. It is more than replacing the current launch expression. Higher capacity is also not necessarily the best shared-PDL schedule: the current adverse cells show much earlier FC2 overlap. No new launch policy, native-handle plumbing, prototype or GPU work is justified by this read-only check alone.
