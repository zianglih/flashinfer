# W4A16 gather/dequant pipeline audit

Source: `82254e206a44b95d9925e4594fac936731f80d21`. This audit starts from the retained implementation, not an old experiment checkout. The one proposed source change is the packed-scale selector below. All other sections are read-only findings; no GPU result is claimed here.

## Candidate: fold scale selection into the existing PRMT

`blackwell/moe_w4a16_utils.py` decodes each independent 16-value NVFP4 block using one E4M3 scale. The fragment wrapper first selects a byte from the packed scale word, then the block decoder uses `prmt.b32 ..., 0x4400` to duplicate that selected byte. Supply the packed word and a compile-time byte index directly, and use `0x4400 | (byte_index * 0x11)` as that same instruction's immediate. The index is an internal Python integer during DSL lowering, not a runtime argument or public tuning option.

The current r2 wrapper preserves its existing two-scale scalar representation, passing byte index0, and applies the fused selection to the existing32-bit packed words used by4/8-scale fragments. It preserves the independent16-value inline-assembly boundary, both toolkit conversion paths, every arithmetic operation, and all pipeline/register/tactic policies. It does not combine multiple dequant blocks into a larger opaque assembly region. The entire source diff is6 additions/3 deletions.

This resumes a paused prototype. The old project's `fc1-gather-20261028/optimization-next-20261029/w4a16-scale-selector-1e4/PAUSED.json` records zero GPU compiles, tests, or performance runs. That prototype was ported unchanged as r1 (`40111f8785707a3554eb4783558e4478899f4f49e87483ed2e225a9d59c1bda8`); its control helper is byte-identical to this project's HEAD (`d5105227bd29382a0182e5427f6d97ca04fc12c62f29dbdcc1737c7b178daf5d`). R1 passed four paired exact/resource cases, but its newly packed two-scale representation added8 FC2 instructions. FC1 removed6 shifts. R2 (`d3afcec4f966c4a30afc4bae528633f96dd4a9a787d712fa8333b1519cbb9ac3`) keeps the original scalar representation to avoid that extra work. Four fresh candidate cases pass; all FC2/finalizer cubins are byte-identical to control, while FC1 removes6 shifts (one capture adds1 R2UR). Resources are unchanged with zero local allocation. Evidence is under `validation/w4-scale-selector-r1/` and `validation/w4-scale-selector-r2/`; performance is still unmeasured.

CPU proof runs the actual old/new wrapper ASTs on6,584 cases covering all three fragment sizes and all256 byte values in every scale position, compares packed input/scale assignments, and verifies4,232 PRMT selector cases. Decoder ASTs are identical after removing only the compile-time selector substitution and signature/doc change; r2 also preserves both existing two-scale extraction branch ASTs. See `verify_w4a16_scale_selector.py` and `w4a16-scale-selector-proof.json`. This proves the byte/dataflow change, not compiler lowering, GPU numerics, resources, or performance.

**Shared scope:** MegaMoE's `_MegaMixedInput` inherits this split kernel's `_transform_tile`, which calls the modified utility. Both MegaMoE FC1 and FC2 are affected. The dense W4A16 GEMM uses a different utility and is unaffected. Before retention: paired native FC1/FC2 captures (including the 32-value/two-scale case), exact tests, no added local storage, selected frozen-winner EP/TP timings across all four models; if those qualify, an isolated GLM5 MegaMoE before/after comparison using the established methodology. Packed scale-word lifetime may increase even though instructions decrease: do not assume register or timing gains.

## Rubin and MegaMoE comparison

- Rubin's regular gather backend (`rubin/blockscaled_contiguous_gather_grouped_gemm_swiglu_fusion.py`) uses four issuer warps and row-index caching outside K, as W4 already does. Hoisting an election around more code is not automatically better: earlier W4 elected-issuer experiments are recorded and closed.
- Rubin's newer MegaMoE gen-specialized kernel (`moe_ep/kernel_src/sm107/next_cutedsl_megamoe/src/sources/kernel_src/rubin/inference/mega/block_scaled_swap_ab_fc12_mainloop_gen_specialized.py`) explicitly uses four gather warps to bound uniform-register pressure, 128-byte swizzle atoms, eight-row/256-bit index loads, and a 160-thread gather rendezvous. Its eight-row ownership requires tile/cluster divisibility that W4's narrow dynamic-N tactics do not universally satisfy. Current W4 already tried broader batched index loading with verified instruction reductions but unresolved V41F prefill losses. Do not copy those constraints or introduce rescue branches.
- W4 MegaMoE (`moe_ep/cute_dsl/megamoe/bf16_nvfp4/megamoe_kernel.py`) uses the same 144/80/96/64 five-WG register budget, with dispatch in the 64-register WG rather than gather. Its `_MegaMixedInput._finish_transform_stage` releases raw SMEM after decoded stores are issued but before the TMEM-store fence. The split base releases after that fence. This narrow ordering difference is lifetime-plausible but is not evidence of speedup; broader early-raw-release changes were already rejected and the current useful work is decode/issue, not a demonstrated fence stall. No edit proposed.

## Avoided repetitions and honest boundaries

The old project's `optimization-next-20261029/CLOSED_LEADS.md`, relevant source patches/results, and `element-scale-ownership-20261029` were checked. Do not repeat: W4 lane-batched routes, 112/128 register redistribution, independent raw/B stage balancing, raw-ready or decoded-slot lookahead deletion, whole-raw-stage early release, role-local TMEM allocation barriers, producer-tail-all-stages, gather relay, or scale/element producer ownership A/B. The thin FC1-only ownership follow-up also ended at +0.107% across 40 cells and was rejected for added participation/role complexity.

The old read-only delayed decoded-acquire proposal was not a measured failure. It was closed later because source-bound iKET means were about 30 ns, near timestamp resolution, and native SASS already interleaved decoded stores with subsequent conversion. The output-acquire scopes were similarly short. Those instrumented scopes are not removable E2E latency estimates. Fresh profiling could reopen a hypothesis if it shows a new mechanism, but the presence of a wait in source is insufficient.

Only one candidate currently has a concrete instruction-removal rationale and no new pipeline state: packed-scale selection fusion. No broader synchronization or register policy change is justified by this audit.
