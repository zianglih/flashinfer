The default `apply_topk_in_fc1=False, in_kernel_fc2_reduce=False` owned W4A16 path has no consumer of expert-pool routing scores. The transfer is redundant for that exact mode, but the current inheritance boundary has no small override that removes it cleanly.

The checked frozen f4c source calls this monolithic method `dispatch_pull` (`kernel_src/cutedsl_megamoe/src/src/token_comm.py:801–1151`); there is no separate `_pull_inputs` method in this revision. It forms the source score base unconditionally at989, performs lane0's remote `ldg_f32_raw` at1041–1049, then stores the pool score at1072–1073. The intervening warp synchronization also orders the existing SF/transport work and must remain. `dispatch_warp_body:1622–1641` forwards both score tensors directly.

Only two owned consumers reference `fc1_input_topk_weights_buffer`: FC1 score multiplication (`epilogue.py:514–528`) when True, and FC2 BF16-before-weighting (`290–298`) when IKR is enabled and the mode is False. In deterministic False mode both compile out. The integrated combine instead reads the source-local `input_topk_weights_buffer` (`megamoe_kernel.py:981–1000,1391–1395,1530–1547`); standalone fallback likewise consumes source scores. Therefore keep source-local score staging and its lifetime. Direct epilogue versus dispatch return does not create another expert-pool score consumer.

There is no nullable-score guard, per-score virtual method, or existing constexpr transfer switch in inherited `dispatch_pull`. Overriding it would duplicate roughly350 lines of scheduling, TMA, metadata, readiness, and flag-batching logic. The raw score LDG is a module-level helper call, not a subclass hook. Passing None would fail at the unconditional iterator/load/store; redirecting to dummy pointers or relying on elimination of externally visible global stores is not a sound substitute.

A future shared ownership/API change could guard just the score-base/load/store with a compile-time capability, defaulting to the existing behavior for other backends. The owned requirement would be `apply_topk_in_fc1 or in_kernel_fc2_reduce`; keep all copy waits, warp barriers, flag batching and ready publication unchanged. This removes one scalar remote FP32 load and one local FP32 store per route in deterministic False mode, not the activation transfer or slot metadata. It is a possible bounded shared-API follow-up, with no measured gain and no implementation under the present protected-source boundary. True mode needs the transfer, so PR9 stays unchanged.
