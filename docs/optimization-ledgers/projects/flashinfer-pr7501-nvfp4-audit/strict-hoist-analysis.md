# Standard-strict reciprocal hoist investigation

Base: 2bd125681b8d34c1835c1bd1916f8b9e3a630f6a. Candidate changes only the strict branch: computes `__fdiv_rn(1.0f, SFScaleVal)` before scale construction and uses that local in the existing guarded expression. It keeps the guard, multiply order, final division, and FLT_MAX clamp.

**Strict-mode control:** #7501 left the standard-strict `vecMax != 0` guard, `__fdiv_rn` operations, and `FLT_MAX` clamp unchanged. We also compiled an equivalent source hoist of `__fdiv_rn(1.0f, SFScaleVal)` before strict scale construction. With the same CUDA 13.2/SM103a toolchain, the complete quantization module's SASS is byte-for-byte identical across both builds (605 function sections; SHA-256 `be35aae82417da9af8f0b12bf41015a5cd6e2b89bd395896a86fb627dd4f234d`). The strict BF16 TMA kernel retains 72 registers and 0 local/stack bytes. NVCC sinks the nonvolatile strict divide back into the nonzero-block branch; the fast path's volatile inline PTX reciprocal stays hoisted. This source-only strict extension is therefore excluded from the PR; no strict performance improvement is claimed.

The dedicated benchmark precompile/verification passed for both source arms at BF16 M1024K7168, with both strict flags set to1. These warmup samples are not performance evidence. No new full numerical suite or counted timing campaign was run because the complete assembly including control encodings is identical. The local tentative batched-strict test extension was preserved in scripts/strict-hoist-experiment.patch but was not executed or shipped.
