# Optional distributed timing sample log

This is an unapplied, one-file benchmark patch. It adds `--log-timing-samples` to `benchmarks/bench_cute_dsl_moe_distributed.py`; the default remains off and `--iters` remains 100. The default full token grid remains 1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024, 2048 and 4096. It changes no kernel, public API, testing utility, tolerance, tactic catalog or primary metric.

When enabled, rank zero prints one `DISTRIBUTED_TIMING_SAMPLES_JSON,` line after each benchmark measurement. The line includes the existing `profile_label`, global token count, rank/world size, timer, external warmup count, requested/actual sample count, graph and cold-L2 settings, the original ordered post-rank-MAX `samples_ms`, and a host `wall_seconds` interval. The unchanged median is then returned to the original CSV reporting path. No sample is dropped, rounded, reordered, reconstructed from a median, or reduced again. Rank one and above do not duplicate the array. Profiling modes retain their earlier return without sample logging.

For CUPTI, the wall interval brackets the existing `bench_gpu_time` call exactly. That includes utility-internal graph preparation, estimate runs, flushes, collection, activity processing and rank aggregation. It excludes the caller's earlier compilation/autotuning/reference checks and external warmup, the utility import, JSON serialization and printing. Consequently this is the total cost of the timing utility, not pure measured-iteration wall time. The sample values themselves remain first-to-last GPU activity spans, MAX across ranks for each iteration, then median across iterations. In the event path, the wall interval covers existing optional graph capture plus the original flush/barrier/event/rank-MAX loop. Host wall time is rank zero's local interval, not a new distributed wall-time maximum.

Only two conditional host-clock reads are added per rank when logging is enabled. No GPU synchronization, allocation, kernel, graph replay, collective or reduction is added. The exact CUPTI call, event loop and `_max_rank_sample` ASTs are preserved. Four artifact-only CPU checks exercise both timers with graph on/off against the original function using mocked device boundaries: disabled return/output/device-call equivalence, enabled sample/median and device-call equivalence, no duplicate rank-one output, and unchanged profiler execution. These are logging-contract checks, not real CUDA validation.

Apply the patch only after scheduling an explicit new benchmark source fingerprint. Both baseline and candidate runs should use identical logging code and the same full token grid. The existing runtime manifest includes this benchmark file, so old ec94 or 20ae source IDs must not silently admit the modified benchmark. Append `--log-timing-samples` to the established benchmark command and keep `--iters 100` for the first complete baseline. Existing frozen setup/adapters and production are unchanged by this artifact.

## Interpreting 20/30-sample stability

For each case, retain all 100 ordered samples and the original median: thirteen token counts times two variants gives 26 cases per arm, 52 across fixed and auto. Compare the first 20 and first 30 medians to the full 100-sample median, then report the range and distribution across all contiguous windows of length 20 and 30. Report signed and absolute relative errors for every token count and both variants; do not select only stable points or substitute a window minimum into a performance table. Contiguous windows reveal ordering effects but overlap and are not independent trials. Fixed-seed subsampling can be an additional descriptive check; neither method establishes cross-run drift or proves that a fresh shorter run will have the same distribution. Existing older runs discarded sample arrays, so this analysis cannot be reconstructed from their medians.

Sampling-count savings cannot be inferred by scaling total run time by20/100 or 30/100: compilation, autotuning, input setup, utility capture/estimate and activity processing have different fixed and variable costs. The new wall interval measures the timing utility's actual share once a case or arm wall interval is also available. Sum of rank-MAX GPU spans is useful activity context, not total host elapsed time or a compiler/autotune breakdown.

## Cheap per-case setup wall proposal

Keep this out of the first patch unless the parent wants an additional metric. The smallest addition is a conditional `perf_counter()` around the existing per-variant benchmark-function invocation in `_run_parallel_mode`, plus one post-return rank-zero JSON line. It includes that function's input/layer setup, compilation/autotuning, reference checking, external warmup, timer utility, and teardown. It excludes shared-weight creation earlier in the token loop, later `gc`/cache cleanup, process initialization and the final reporting barrier. Subtracting the matching timer wall interval gives a **setup/warmup/teardown residual**, not compilation-only or autotuning-only time. No extra synchronization should be introduced merely to time this host boundary. A separate shared-weight wall interval could be recorded around its existing call if needed; it must not be charged to both variants.

Existing EP `run_setup_phase` callbacks provide a later narrow place to time individual split setup phases, including tactic selection, because they already synchronize on completion. Mega's existing `layer.warmup(tensors)` similarly provides a combined first-use compilation/autotuning boundary. Separating those internals further would require additional instrumentation and is not proposed here.
