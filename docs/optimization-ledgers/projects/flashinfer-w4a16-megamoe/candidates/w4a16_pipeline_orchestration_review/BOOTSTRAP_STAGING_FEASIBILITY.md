# Input staging in Mega bootstrap: bounded feasibility

Read-only assessment of retained commit `542224a1b4619f65d4730bb4fba3daf5c1cfe097`. No prototype, primary/vendor change, capture or GPU run. A launch-fusion design is feasible without another global barrier; true same-CTA copy/count-preparation overlap has no existing handoff through the unchanged transport entrypoint.

## Actual dependency sequence

1. [Owned staging](../../flashinfer/flashinfer/moe_ep/backends/mega/kernel/sm100/bf16_nvfp4_bf16_cutedsl/staging.py#L63) currently copies live BF16 activations and FP32 scores, converts IDs to int64, and fills every capacity-tail ID with −1. It preserves activation/score tails and falls back for empty, strided, misaligned or aliased views and capture-time specialization misses. Its [device worker](../../flashinfer/flashinfer/moe_ep/backends/mega/kernel/sm100/bf16_nvfp4_bf16_cutedsl/staging_kernel.py#L41) launches one 128-thread CTA per capacity row.
2. Mega receives the staged buffers through [TokenCommArgs](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/megamoe_kernel.py#L581). Transport's [dispatch_prep](../../flashinfer/flashinfer/moe_ep/kernel_src/cutedsl_megamoe/src/src/token_comm.py#L602) reads staged IDs twice, at lines645 and692, to count experts and scatter route slots. These reads happen before the count exchange.
3. [dispatch_barrier](../../flashinfer/flashinfer/moe_ep/kernel_src/cutedsl_megamoe/src/src/token_comm.py#L719) first joins all dispatch CTAs via `software_grid_sync`, then publishes peer counts. Its existing system release/acquire NVLink barrier and final grid join complete before pull. [grid_sync.py](../../flashinfer/flashinfer/moe_ep/kernel_src/cutedsl_megamoe/src/src/grid_sync.py#L25) uses a local dispatch barrier, leader GPU-release arrival, completion polling/fence, and another local barrier. These operations already publish route-slot stores from every CTA.
4. [dispatch_warp_body](../../flashinfer/flashinfer/moe_ep/kernel_src/cutedsl_megamoe/src/src/token_comm.py#L1563) calls prep→count barrier→named9 arrival→pull with no caller hook between those steps. Named9 has only dispatch128+scheduler32 participants here; dispatch arrives without waiting. The [scheduler wait](../../flashinfer/flashinfer/moe_ep/kernel_src/cutedsl_megamoe/src/src/token_comm.py#L570) cannot delay peer pull on behalf of separate copying roles. Remote BF16 TMA reads and FP32 score loads occur inside pull; input sources must be ready by then.

## Existing synchronization that could be reused

An owned copy worker could finish **before** the current [pipeline initialization arrival/wait](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/megamoe_kernel.py#L1088). Every CTA would locally hand its writes to dispatch before dispatch enters the unmodified body. The later count grid/system barrier would then publish all source x/score writes before any peer pulls them. No new global counter or barrier round is required.

There are two exact constraints:

- **IDs must be CTA-local to their first consumer.** Match prep's assignment: `((cta*4 + warp)*(32//topk) + lane//topk)`, stepped by `sm_count*4*(32//topk)` and guarded by its active lanes. A simple `row=cta; row+=sm_count` ID copy would leave some IDs to another CTA, while prep reads them before the first grid barrier. Include the full capacity tail, not only live T. BF16 x and FP32 scores may use balanced grid striping because no CTA reads them until after that grid/system barrier; they do not need the ID partition.
- **The present C2 initialization barrier is relaxed.** The saved emitted PTX contains `fence.mbarrier_init.release.cluster; barrier.cluster.arrive.relaxed; barrier.cluster.wait`. The first fence orders mbarrier initialization, not ordinary input stores. A copy before that arrival therefore needs a nonrelaxed release arrival or an appropriate explicit ordinary-memory ordering edge. C1's existing CTA synchronization already provides the local handoff. The [official PTX barrier specification](https://docs.nvidia.com/cuda/archive/12.1.1/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-barrier-cluster) explicitly gives relaxed arrival no prior-memory visibility guarantee. The archived DSL helper's comments at `candidates/cuda132_recovery_0909e/dsl_pipeline_source/cutlass/pipeline/helpers.py:1006–1011` are reversed; its called primitive and actual PTX, not those comments, determine semantics.

This arrangement serializes each CTA's copies before its own count preparation; different CTAs can progress independently until the existing grid barrier. Copying after initialization in idle decode/epilogue roles would lack a handoff into dispatch's count barrier. Neither the 416-thread TMEM allocation wait nor named9 covers that dependency. Adding copiers to dispatch's hardcoded 128-thread barriers would change its participant contract. Splitting/reimplementing the shared body to insert a later join would violate the requested transport boundary and is not proposed.

## Cost and recommendation

The copies remain necessary: public inputs need not reside in symmetric peer-addressable storage, and peers use the existing symmetric destinations. Fusion removes one launch/graph node and may share bootstrap overhead; it does not remove BF16/FP32 read/write traffic. It also must keep active-row copy parallelism: at topk8 dispatch assigns 16-row blocks, so blindly assigning all BF16 copies by that partition activates only 32 CTAs for local n512. Independent balanced x/score striping avoids that restriction.

This is not a small deletion of `stage_inputs`. [The backend](../../flashinfer/flashinfer/moe_ep/backends/mega/kernel/sm100/bf16_nvfp4_bf16_cutedsl/backend.py#L171) presently materializes workspace buffers before compute/autotune; it returns no payload, and compute receives only workspace, weights and output. Deferring the copies requires owned workspace references to the raw inputs and explicit propagation through autotune and raw launch/thunk paths. A fused path must pass the three source descriptors plus genuinely dynamic live T, preserve raw staged calls, same-pointer shape changes, graph lifetimes, and all existing fallback/alias semantics.

The frontend presently owns one `_mega` compiled object per frozen configuration. Its descriptors always see BF16/int64/FP32 symmetric input buffers. Only the separate stager specializes on original ID dtype; int64 warmup followed by an int32 capture miss currently falls back to Torch without recompiling Mega. Folding the raw source descriptors into Mega introduces source-ID dtype and staged-versus-unstaged specializations. A graph-safe fallback would therefore require an already compiled compatible Mega path, likely explicit compiled variants or precompilation, rather than merely keeping the Torch copy fallback. The existing pointer-only raw launch key assumes fixed padded shapes; raw views additionally need shape/stride identity and dynamic live-N handling. The standalone worker/fallback cannot simply be deleted. Reusing its vector-copy body through an owned worker would avoid duplicating arithmetic, but row scheduling and the cache/lifecycle contract still add code.

History Entry054 (`w4a16_optimization_experiments.md:4340`) retained fusion of several staging operations into today's one launch; Entry055 tested static copy rounds. Neither is kernel-bootstrap fusion. Its historical 3.36% whole-AUTO change is not the remaining launch's cost. The [current-best-0909d T4096 kernel CSV](../../profiles/current-best-0909d-nsys-t4096-001/ep_w4a16_megamoe_t4096.kernels.csv) does contain the fused `Bf16InputStage`: 16 launches average **7.118 microseconds**. This is captured commit `056ce0d090d425ee09171e47f6faea61c76c9551` / source `af938d808556e72925933208f0844cd92f44dff5cc7f407b050897c5660b2e9e`, not the earlier pre-fusion copy sequence. Those eager instrumented calls have substantial rank skew ([capture provenance](../../profiles/current-best-056ce-0909d/README.md)); they are not current latency or a removable-savings bound. Fusion still executes the copy itself.

Recommendation: classify whole-bootstrap launch fusion as technically credible but an API/lifecycle and source-size tradeoff, not an established substantial overlap gain. The stronger idle-role overlap proposal has no clean existing handoff within the allowed transport interface. Do not claim performance improvement or remove the current stager until the source-plumbing cost is acceptable; no new transport fork, public knob, or validation framework is justified by this audit.
