# Paired N64 decoded-weight reuse: source-only feasibility

**Feasible storage, real orchestration change, uncertain value.** Two N64 token blocks could accumulate into the existing two64-column banks while sharing each decoded K256 weight tile. There is no source-visible TMEM or BF16 MMA instruction obstacle. It provides the same128-token weight reuse already available through N128, with different accumulator release granularity and operand buffering. It is not free additional reuse on top of N128.

This audit uses the retained compute/layout/epilogue bodies, unchanged by the active scheduler experiment. No implementation, native compilation, GPU work or tactic expansion is proposed.

## Capacity and what differs

[`_MegaMixedInput`](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/megamoe_kernel.py:74) derives one accumulator's columns from its real CuTe fragment, asserts columns=N, and allocates128 columns per decoded K256 stage.

| Organization | TMEM columns | Decoded passes for two full64-token blocks | Accumulator ownership |
| --- | --- | --- | --- |
| Retained N64 | ACC2×64 + D3×128 =512 | Two | One output tile per stage; MMA and epilogue alternate stages |
| Retained N128 | ACC2×128 + D2×128 =512 | One | One128-token tile per stage; another whole128-token tile can overlap its epilogue |
| Paired N64 | Two64-column banks + D3×128 =512 | One | Both banks belong to the same shared-K pair until its results finish |

The paired design also retains N64-sized activation storage. Current selected N64 has raw5/B3/D3; N128 has raw4/B3/D2. However, an unchanged N64 B3 ring holds only three64-token activation tiles: one-and-a-half pair-K steps, versus three full pair-K steps in N128 B3. Pairing still transfers the same activation bytes as N128, through two N64 TMA issue/transaction sequences. Each K256 pair also issues32 K16 MMA atoms rather than N128's16 wider atoms; equal arithmetic work does not imply equal issue cost. The two decode WGs can keep their existing cooperative split of one A tile.

The closest prior capacity experiment is [Entry059](../../w4a16_optimization_experiments.md:4681): N128/ACC1/D3 was numerically valid but not retained. Its128 accumulator columns and384 decoded columns match the pair. Paired N64 is distinct chiefly because its two64-column banks can publish/release independently and its B ring remains narrower. It does not make that prior result irrelevant or prove the new design loses.

Pairing two N128 blocks would instead seek256-token reuse, using256 accumulator columns plus D2. That is the same reuse width and TMEM split as the closed N256 wider-work direction discussed in the [earlier orchestration audit](README.md:25), whose tiny gain the user explicitly rejected. Its split128-column releases and narrower/interleaved B loading could differ, but renaming the width/ACC tradeoff as pairing is not a new mechanism. Any distinct case would have to rest on a concrete partial-release/epilogue overlap protocol, not rediscovering wider weight reuse.

## Required pipeline changes

- **One A, two B operations per K.** The [MMA helper](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/dynamic_mainloop.py:103) accepts explicit C/A/B fragments; both calls may reuse the same A pointer with different C banks/B stages. Each result preserves its own K16 accumulation order and starts with accumulation disabled at K0. The [current MMA loop](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/megamoe_kernel.py:1319) releases A after one MMA tile. A pair must release A only after both consumers have been issued through the existing UMMA completion protocol; B can advance/release after each individual operation. Both CTAs must agree on pair identity and the second block's valid count.
- **Activation loading must interleave by K.** The [current loader](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/megamoe_kernel.py:1180) completes all K tiles for one work record before consuming another. A shared-K pair instead needs `B(row0,K0), B(row1,K0), B(row0,K1), ...`, with logical K separate from the physical B stage count. Leaving the loader unchanged would supply the wrong B tile or fill its finite ring before the second row's K0 can arrive. Each64-token block retains its own dispatch-ready/FC1-done certificate, actual valid count and nonleader dynamic-N shift. Readiness for row0 never certifies row1.
- **Pair ownership must be explicit.** The [mapper](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/fc1_fc2_fuse_sched.py:901) runs feature tiles before token rows. Adjacent claims generally have different weight-M tiles, so they cannot simply share A. A pair must own the same expert/phase/feature-M and two distinct token blocks exactly once. That requires a paired work domain or another explicit ownership scheme, not independent atomic lookahead that may encounter another cluster's block. Weight/raw producers and both decoder WGs must consume the pair once, while epilogue/output completion retains both records. Odd rows, expert boundaries and phase/group boundaries need an unpaired tail. Merely adding a second MMA call does not meet the scheduler consumer contract.

## Epilogue and overlap cost

The [accumulator pipeline](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/megamoe_kernel.py:1052) has two independent stages. The [FC1 epilogue](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/epilogue.py:417) consumes one stage, performs gate/up scaling and SwiGLU, then transposes in-place within that stage. Its [last scratch reads](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/epilogue.py:515) precede release; final BF16 conversion/stores follow from registers. Bank0 columns0–63, bank1 columns64–127 and decoded columns128–511 remain disjoint, so this scratch does not make pairing impossible. Both completion publications must still follow their actual stores and the existing next-record/BAR1 ordering ([epilogue loop](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/epilogue.py:147)).

The cost is lifetime: both paired outputs finish near the end of the same K loop. Unlike retained N64, epilogue0 cannot overlap the entire computation of tile1; unlike retained N128, there is no spare128-column bank for the next whole pair. A straightforward implementation that acquires both banks up front waits for both prior outputs before starting another pair.

Independent64-column releases could recover some overlap: commit result0 after its last MMA, and start the next pair's row0/K0 when bank0 returns, acquiring bank1 later. But the shared A tile cannot be released or the ordinary lockstep pair advanced until row1/K0 consumes it. Running row0 much further ahead would need retained-A bookkeeping and remains bounded by D3. This is a substantive MMA/epilogue scheduling redesign, not an automatic benefit of the current two-stage pipeline. FC2 has analogous independent routing/return bounds and per-record completion obligations.

**Disposition:** retain as a lower-confidence macro design, not a stage-only retry or a claimed speedup. Its strongest possible advantage over N128 is D3/raw5 plus finer bank release; its costs are reduced whole-tile accumulator overlap, shallower effective B lookahead, more issue operations and paired work plumbing. A reason to elevate it would be evidence that current N128 loses chiefly to decoded-weight backpressure while its accumulator overlap is of little value. Capacity arithmetic alone does not establish that condition.
