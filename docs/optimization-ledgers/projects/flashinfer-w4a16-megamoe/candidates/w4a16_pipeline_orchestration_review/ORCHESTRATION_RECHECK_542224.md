# Orchestration recheck at retained 542224

Read-only source/history audit at `542224a1b4619f65d4730bb4fba3daf5c1cfe097`. No production change, capture, runtime check, or new benchmark request. This note supersedes the *next candidate* recommendation in the older `EARLY_WEIGHT_DECODE_AUDIT.md`: exact-tail reduction and per-K FC2 readiness have since completed validation/performance and were not retained.

**Conclusion:** no distinct next macro implementation is sufficiently supported by this bounded audit. There is real overlap already, and the remaining bounds require either more storage, different work ordering, or a broader host/metadata contract. This is not a claim that all possible redesigns are exhausted.

## Existing overlap and necessary gates

- [Shared dispatch](../../flashinfer/flashinfer/moe_ep/kernel_src/cutedsl_megamoe/src/src/token_comm.py#L1563) performs route preparation and count exchange, arrives at scheduler named barrier 9, then begins activation pulls. The scheduler is released before payload pull completes. The [owned scheduler branch](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/megamoe_kernel.py#L1124) needs the exchanged expert sizes to map work; it does not wait for all activations.
- [Weight warp 5](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/megamoe_kernel.py#L1135) and [both decode WGs](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/megamoe_kernel.py#L1224) have no activation-readiness gate. Only activation warp 6 waits for input readiness or FC1 completion. [MMA](../../flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/megamoe_kernel.py#L1300) joins the decoded and activation streams in K order. FC1 dequantization therefore already overlaps remote pulls; FC2 weights/decode can run while FC1 output is unavailable.
- [Work-record consumption](../../flashinfer/flashinfer/moe_ep/kernel_src/cutedsl_megamoe/src/moe_nvfp4_swapab/moe_persistent_scheduler.py#L170) copies metadata into registers and immediately releases its shared pipeline slot. It does not hold scheduler storage until compute finishes. Readiness peeks annotate work rather than block scheduler publication.
- Current TMEM is full: ACC2 plus decoded D3 for N64 or D2 for N128 uses 512 columns. Raw/SF buffering runs ahead independently, but completed decode cannot continue indefinitely when activation or accumulator consumption stops. Alternating full K tiles between the two decoder WGs does not add storage; it changes barrier participation, odd-K/work-transition ownership and register pressure. The existing [early-decode audit](EARLY_WEIGHT_DECODE_AUDIT.md#alternating-whole-k-ownership) records those untested costs. No current evidence identifies them as worth replacing the compact split-decoder reuse.

## Sibling and split comparison

[BF16 Mega](../../flashinfer/flashinfer/moe_ep/kernel_src/cutedsl_megamoe/src/moe_bf16_glu/kernel_bf16_glu_fc12.py#L1217) and [NVFP4 W4A4 Mega](../../flashinfer/flashinfer/moe_ep/kernel_src/cutedsl_megamoe/src/moe_nvfp4_swapab/kernel_fc12.py#L1542) use the same early atomic claim / deferred static decode distinction. Atomic initialization can overlap common setup; static mapping must wait for dispatch-produced sizes. Current W4A16 already follows that pattern.

Split W4A16 provides a useful contrast, not a directly missing Mega optimization. Its [scheduler](../../flashinfer/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py#L1204) reads routed-tile metadata before the preceding activation grid completes. Only its [activation TMA role](../../flashinfer/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py#L1389) executes the PDL wait; [weight loading](../../flashinfer/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py#L1454) starts independently. FC1 can announce dependent launch from that weight role, while FC2 activation loading still respects completion. The [host sequence](../../flashinfer/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16.py#L406) has already constructed route metadata via sort before permutation/FC1/FC2.

Mega instead reads staged IDs inside dispatch preparation **before** its count grid barrier. Its useful expert-specific weight work needs the resulting counts/mapping. Merely adopting an activation-only PDL wait cannot move this metadata dependency. Without changing that contract it could at most overlap generic setup, while current intra-kernel publication already enables the useful weight/activation overlap. This is a source inference, not a PDL timing result.

## Closed directions and still-open costs

- Startup claim reorder after common initialization: [Entry080](../../w4a16_optimization_experiments.md#entry080--first-atomic-claim-after-common-pipeline-initialization), validated but not retained. Stage-only raw/B changes already include Entries044, 052 and 081, plus raw7/B2/S3; a deeper-ring proposal alone is not new.
- First-fragment/late-acquire, ACC1, K128, N256, CLC and operand-release directions remain closed under the current scope. No repeat is proposed.
- [Exact-tail reduction](../../w4a16_optimization_experiments.md#exact-tail-reduction-complete-table-and-non-retention) and [per-K masks](../../w4a16_optimization_experiments.md#fc2-readiness-masks-complete-validation-and-non-retention) were functioning, validated designs. Their small mixed whole-run changes did not justify retention. The current whole-row FC2 gate is not an overlooked untested opportunity.
- [Bootstrap staging fusion](BOOTSTRAP_STAGING_FEASIBILITY.md) can reuse the existing global count/publication barriers only with correct local copy ownership and release ordering. True same-CTA idle-role copy/count overlap has no existing handoff through the unchanged shared body. Raw descriptors also introduce source-ID dtype and staged/unstaged Mega variants, dynamic live-N and view-cache identity, graph fallback/precompile and lifetime plumbing. These are substantial untested costs; eliminating one launch does not eliminate staging traffic. Historical fused `Bf16InputStage` at old056/current-best0909d averaged 7.118 us at T4096 over skewed instrumented eager calls, not a current savings bound.

A genuinely broader future design could change metadata preparation or work assignment to make independent expert work available earlier, or change storage/lifetimes to permit more decode runahead. Neither is a small removable barrier, and neither currently has a source-backed expected payoff sufficient to select an implementation. Preserve these design questions without adding a transport fork, public tactic axis, or speculative trial.
