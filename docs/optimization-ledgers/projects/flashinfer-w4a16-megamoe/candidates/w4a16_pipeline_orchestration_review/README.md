# W4A16 pipeline orchestration review

The established MegaMoE orchestration is largely already present. Two structural designs merit a feasibility pass; neither is an implementation proposal ready for timing, and neither has new performance evidence. No third direction from this bounded comparison clears the same bar.

This read-only review used the pending implementation-cleanup source `eb9cc9a1877da7dfea0f35ff51ffbc1666036fdcbe1500d109ec46f56fd824df`, manifest `51b972d9059c321a523da38a948aee5c7050ecd8efed49734a42592d4f0ebb3d`, above published `dde36ec13cacb0ee8768275ff8ab660d19748a7d`. The ten cited pipeline files match that manifest. Cleanup validation/publication remains a separate task. This note made no repository changes, native captures, tests, remote calls, benchmark runs, or result reconstruction.

Paths below are relative to `flashinfer/`. `owned/` means `flashinfer/moe_ep/cute_dsl/megamoe/nvfp4_w4a16/`; `drop/` means `flashinfer/moe_ep/kernel_src/cutedsl_megamoe/src/`.

## 1. Wider routed-token work tile with a different TMEM allocation

**Status: concrete structural candidate; allocation and epilogue feasibility unverified.** W4A4 explicitly admits N128/N256 (`drop/moe_nvfp4_swapab/kernel_fc12.py:225–248`) and processes its output as 64-token subtiles. W4A16's BF16 descriptor helper already accepts allocated N256 (`owned/dynamic_mainloop.py:117`), but its public/kernel/epilogue contracts admit only N64/N128. Descriptor acceptance is not kernel support.

The present TMEM allocation fixes two accumulators, leaving two or three decoded K256 tiles (`owned/megamoe_kernel.py:52–93`). At N256, two accumulators leave no decoded storage. A possible structural layout is **one 256-column accumulator plus two 128-column decoded tiles =512 columns**, preserving tile-local TMEM decoding and both decoder WGs. This also requires changing the accumulator pipeline/storage/layout consistently (`:720–737,1060,1318`; `owned/epilogue.py:97–110`), admitting four output subtiles and refitting raw/activation SMEM. Merely adding N256 to the catalog is invalid.

The mechanism is fewer complete packed-weight load/decode passes when an expert's routed rows span multiple N128 work tiles. It is distinct from rejected ACC1/N128: that experiment purchased an extra decoded slot without increasing the number of rows served by a decoded tile. Here wider work buys reuse, while giving up accumulator overlap. Tradeoffs are reduced MMA/epilogue concurrency, larger activation storage, potentially shallower operand rings, more padding/storage, longer per-task epilogues and fewer tasks for load balancing.

For the existing global-T/E256/top8 workload, mean routed rows per expert is `T*8/256 = T/32`: T4096 reaches128; T2048 reaches64. N256 therefore mainly helps experts exceeding128 near the upper end or under skew. Dynamic N already shortens arithmetic for partial tiles, but does not remove the larger physical buffers or lost accumulator overlap. This is not a predicted broad gain over8–4096.

**Smallest defensible validation:** first admit one M256/N256/K256/C2 layout in native code, verifying actual TMEM/SMEM allocation, no spills, stage wrap and four-subtile release/completion behavior; cover both return paths before claiming general support. Use the existing shared numerical reference for full/partial/empty tiles and changing expert/rank routing, including the128/256 row boundaries, with unchanged tolerances and both scheduler modes. Only after these gates consider this one geometry alongside the retained choices in the original full13-row AUTO protocol; do not combine a new stage/catalog grid with it. Record actual routed occupancy, resources and chosen tactics rather than infer reuse from global T alone.

## 2. Exact post-FC2 reduction inside the completed Mega tail

**Status: secondary feasibility-only design; not a ready-made sibling mode.** BF16/W4A4 show the structural benefit of in-kernel combine (`drop/moe_bf16_glu/megamoe_kernel_bf16.py:15–32`; W4A4 config's `in_kernel_fc2_reduce`). Their BF16 atomic/bulk-add modes are **not compatible substitutes**: they may apply routing before FC1 quantization/activation boundaries and accumulate BF16 in nondeterministic order. W4A16 requires the BF16 FC2 result followed by FP32 routing and FP32 accumulation.

Current W4A16 calls the existing separate `TopkReduce` after Mega (`owned/frontend.py:380–419,578`). Its exact BF16 path is `drop/moe_nvfp4_swapab/topk_reduce.py:367` onward, including ordered top-k traversal and architecture-selected arithmetic. A structural alternative would retain the current BF16 combine buffer and this exact math, then assign final reduction work to existing resident threads **after inherited communication tail completion**. This removes a kernel launch/phase; it does not eliminate combine-buffer traffic or claim overlap of dependent combine loads with ongoing peer writes.

The relevant completion boundary is `drop/src/token_comm.py:1783–1870`: an all-role CTA rendezvous, then dispatch-warps-only cross-rank drain, shared reset/publication, and local reset. Consequently, ordinary compute warps returning from `kernel_tail` are not by themselves proof that dispatch cleanup finished. A local handoff after the dispatch subset returns is required before those warps read combined output. This design must preserve that boundary and all resets, avoid another cross-rank protocol, retain five WGs, and provide an output pointer/work mapping without affecting the main-loop register allocation. Keeping reduction ordered is essential; swapping in BF16 REDG is not an option.

Tradeoffs are longer resident-kernel duration, extra main-kernel code/register pressure, a local rendezvous, and potentially less suitable reduction parallelism than the current separate grid. Earlier instrumented traces found limited absolute reducer work (ledger Entry033); they do not establish a current gain. This is also different from the earlier PDL note: no early dependent reads or speculative concurrent reducer launch is proposed.

**Smallest defensible validation:** first prove exact final visibility and the unchanged ordered FP32 arithmetic in native/source review, for direct and reused return. Reuse existing precision-cancellation, empty/skew/refill and eager/graph tests, retaining all tolerances and exact checks. If those pass with acceptable resources, compare one complete retained and one complete fused-tail13-row run using the original full-forward metric. No transport rewrite or broad tuning sweep belongs in this trial.

## Excluded repetitions

The ledger already contains group256/1024, scheduler-depth and B/raw-depth sweeps, readiness probing, ACC1/N128, K128/extra B stages, first-claim overlap and shared-operand completion experiments (Entries043–048,052,056–057,059–064,075,080–082). Their old negative results are not current timings, but they rule out relabeling those exact designs as new missing orchestration. The current audit also excludes custom transport/wait1, CLC, one-decode-WG designs, global/shared BF16 weight materialization, instruction-level dequant changes, and incremental buffer-lifetime releases. BF16/MXFP8 TMA epilogues pay explicit output-SMEM/staging costs; their existence alone does not establish an improvement over W4A16's deliberate direct BF16 stores.

Proceed with the N256 feasibility question first if a new structural trial is selected. Keep the fused-tail idea as a separate, lower-confidence design. Neither should interrupt completion of the current cleanup validation.
