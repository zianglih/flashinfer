# Two pending BF16 pool writes — held

Source review supports a native trial of **only** the F>1 pre-store `cp_async_bulk_wait_group(0)` → `(1)` and its adjacent comment. Base is frozen source `600cff5f7e179d31f6eec8ba31ee6724046ee9c589fa5164162ba04fd2415776`, transport `55650c3c06f62560c0beb4340b6460ea1de9c981250dc21ec8387360c9debfba`. No primary source, runtime helpers, freeze, remote, or GPU changes accompany this proposal. Four dispatch warps, two decode groups, five total groups, buffers, stages, registers, and public knobs are unchanged by source construction; native resources are not yet measured.

`token_comm.py` references below are to the copied base/proposed transport under this candidate. Inherited files are under `flashinfer/moe_ep/kernel_src/cutedsl_megamoe/src/src/`.

- **Group ownership and bound.** Each executed token issues one pool copy and commits it in the same elected scope (`token_comm.py:257–280`). Input copies use mbarrier completion, not bulk-group completion (`ptx_helpers.py:46–90`). Starting with no pending groups, wait1 at256 leaves at most one older destination group; the current commit leaves at most two. Completed groups only reduce this bound. The unchanged full-mask deterministic issuer must be verified in native output; election is not used as a memory fence.
- **Scratch reuse.** The unchanged all-lane READ0 at202 precedes the next input-copy election at204, completing source reads of *all* older groups before the sole per-warp buffer is overwritten. Input mbarrier completion at238–245 still precedes the current pool copy. Thus allowing a second pending destination write adds no shared-memory reader or buffer lifetime. The input phase toggles exactly once per token at310.
- **Destination and publication.** `token_idx` partitions the received rows across global warps (99–106,312); expert padding and `pool_token_idx` at223–226 assign distinct pool rows. Neither a later token nor another warp overwrites an outstanding destination. Metadata and FP32 routing stores remain at270–280. No consumer may use the row on the strength of issue/commit alone: full wait0 plus warp synchronization still precedes the GPU-release publication at284–305 and316–319, including the ordinary metadata/weight stores and rotating publishing lanes.
- **All manual batches.** The inherited constructor accepts F1–32 (`token_comm.py:413–417` in the inherited file). The tracker starts at phase0 and always accumulates phase0; its only in-loop fire condition here is reaching F, not changing a task address (`flag_batch.py:69–88`). F2 can have two groups before its existing immediate publication drain; F3–32 have the same two-group cap independently of batch size. Each pending counter address fits the existing F≤32 lane rotation. F1 excludes the changed branch at compile time and continues to drain/publish every token.
- **Tail and return.** Zero-work warps issue no groups; one-token and partial batches drain at316 before firing. Full batches already drained in the loop. The final warp sync and returned phase/counts are unchanged. Inherited `dispatch_warp_body:1622–1670` therefore enters reuse-dispatch token return with no outstanding dispatch groups and the same scratch/mbarrier phase; direct return preserves the same final drain. No destination writes escape the dispatch handoff.

[PTX 9.4 bulk waits](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#data-movement-and-conversion-instructions-cp-async-bulk-wait-group) define N as the permitted number of recent pending groups; the full form includes destination completion/visibility to the issuer, while READ waits only for source reads. [Commit groups](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#data-movement-and-conversion-instructions-cp-async-bulk-commit-group) are per thread. [Election](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-elect-sync) selects the same leader for the same member mask. These distinctions underpin the unchanged scratch/publication boundaries above.

History: `w4a16_remaining_transport_overlap_4bf.md` established the prior one-pending bound, not its necessity. `w4a16_optimization_experiments.md:7200–7207` mentioned wait1 only in the unselected two-buffer design; the bounded ledger/candidate search found no prior trial of this one-buffer immediate change.

Native admission should verify only the intended F>1 full-wait immediate changes, READ0 stays before overwrite, full publication/tail waits and full-mask issuer remain, and no resource/spill or unrelated scheduling regression appears. F1 should remain byte-equivalent. The existing frozen 14/38 cohort has 12/13 pulls per active warp at F4/F8 plus F1, partial tails, empty/refill/uneven sources and both return modes; reuse it without expanding the matrix. F2–32 correctness here is source-derived, not an assertion that every manual value was executed.

The extra pending destination may overlap write latency but may instead add memory-system pressure or simply move waiting to publication. READ0, source pull latency, and workloads with too few per-warp tokens can limit the opportunity. This is a readiness recommendation, not a throughput result.
