# First16: fixed epilogue144 / decode96 register split

This is the existing two-edit register proposal rebased onto the current first16 Mega kernel. It remains an unapplied, independent source candidate; no owner, native harness, remote or GPU work is added. The same kernel bytes are used by first16 a9 and the prospective UInt16 scale refinement, so this patch can be considered after the next completed source is selected. It does not declare that future full-source owner.

The executable changes are only removal of decode's decrease(80) and epilogue increase(176) becoming increase(144). Both decode groups retain their initial96 registers. The control group stays80 and dedicated dispatch stays64. Five WGs, exactly two decode WGs, 640 threads, actual initial REG96 and the 61440-register pool remain fixed. Shared transform/utility files, first16 predecode ordering, epilogue implementation, all predicates/barriers/stages and the public catalog are untouched. The copied original AST validator reverses these two statements and proves whole-module equality.

The donor arithmetic gives the concrete startup hypothesis: control returns 128*(96−80)=2048 registers and dispatch returns 128*(96−64)=4096, exactly the6144 needed for epilogue96→144. Epilogue allocation therefore no longer requires either decode group's donation. This removes a donation dependency at CTA startup; it does not remove any steady-state raw/decoded/accumulator pipeline wait or establish that startup is currently expensive. The existing TMEM rendezvous and role entry ordering remain identical. Decode has no new increase or equality decrease; this keeps the already-reviewed CUTLASS convention of leaving a group at its initial allocation.

The recent native pairs provide useful limits rather than a prediction:

- Both first16 controls and the private UInt16 refinements actually compile at REG96/640 with the original four redistribution sites and zero local accesses in N128/N64 C2 epi-return fixtures. First16 already carries its first sixteen decoded BF16 values across the decoded-stage wait at decode80. The UInt16 variant holds additional decoded payload before the first store, also without a spill. Thus no observed spill establishes a need for96, though that cap could change scheduling.
- The N128 main epilogue code regions explicitly name registers through R111; N64 reaches R107. Those match the earlier modern observations. The saved native JSON records each exact interval and instruction, including the FC2 pointer-high calculation. These indices are not simultaneous-live counts, complete CFG peaks or proof that144 is sufficient after recompilation.
- Static FC2 early release and all epilogue scratch ownership remain unchanged in source. Lowering the epilogue cap can still alter its instruction scheduling or introduce locals, so a fresh source-correlated native check remains essential. There is no evidence yet that any performance effect would come from decode throughput rather than startup/compiler scheduling.

Reuse the existing strict capture-helper pattern when a completed baseline is selected. The control must show exactly DEC80 / DEC80 / INC176 / DEC64; the candidate exactly DEC80 / INC144 / DEC64 (0x50 / 0x90 / 0x40). Bind that expected signature to the exact kernel content and retain actual REG96/640, two decode groups, one sealed compile and zero GPU calls. Do not loosen the existing four-site assertion or pass arbitrary cap lists. This artifact supplies only that pattern, not another helper/owner/runner framework.

A later matched native gate should inspect locals by role, MMA/CFG duplication, loaded/scaled payload liveness, unchanged arithmetic/loads/stores/barriers and epilogue scratch-load/fence/release order. Actual correctness/progress and performance remain separate, using the established geometry/return/tail/lifecycle and full timing coverage. The candidate is general-purpose and creates no shape selector or public register knob. Alpha relocation remains a separate candidate.

`epi144-decode96.patch` is applicable to the current local kernel without applying it. `validate_source.py` is byte-identical to the earlier proposal's validator. Its AST proof, Ruff/format and patch applicability checks pass locally. `saved-native-observations.json` contains only reads of completed captures, with explicit limits. Original proposals, captures and production files are preserved.
