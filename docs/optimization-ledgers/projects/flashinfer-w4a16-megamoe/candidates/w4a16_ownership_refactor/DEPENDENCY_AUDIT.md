Read-only audit of the primary FlashInfer checkout, 2026-09-09. HEAD is `fa2a892038f54def18c83571e50b47804f8de1cb` (the shared-release revert; retained tree matches056ce), with the seven uncommitted CLC files. Subsequent organization decision: the user explicitly chose the owned sibling
precision directory `cutedsl_megamoe/src/moe_nvfp4_w4a16/` and thin
`cutedsl_megamoe/shim/w4a16.py`. This authorizes that new directory despite the
prior verbatim-drop rule; existing vendored files remain unchanged. The initially
proposed separate `cutedsl_w4a16_megamoe` package was rejected and removed.
The dependency findings below describe the saved pre-refactor source. See
`EPILOGUE_REFACTOR.md` for the completed local epilogue extraction.

The current W4A16 implementation owns its mixed-input launch, online decode/BF16 MMA and most FC1 arithmetic, but it still **depends on W4A4 core pipeline classes and constructors**. Moving or renaming the existing classes would not remove that dependency. The clean boundary is an independently owned W4A16 implementation, with explicit constructor/workspace and BF16 epilogue behavior, importing only neutral transport, mapping and math utilities. Exactly two decode warp groups remain part of the W4A16 kernel contract; no shared-operand-release change belongs in this cleanup.

## Important transitive boundaries

- W4A4 Mega import loads `kernel_fc12`, which loads its scheduler/mainloop/epilogue graph. W4A16 currently reaches this both through direct inheritance and through the BF16 utility import. A new class that retains either base is not independent.
- `src/token_comm.py` imports `grid_sync`, `ptx_helpers`, `flag_batch`, `sf_swizzle` and only `_nanosleep`/`spin_wait` from `nv/moe_utils.py`. That utility module imports Cutlass, not `kernel_fc12` or the epilogue. Dtype-specific branches inside a transport protocol do not make it a W4A4 core pipeline; W4A16 supplies BF16 and no SF plane.
- `nv/moe_persistent_scheduler.py` defines generic work records, ring storage and producer/consumer machinery without importing a compute kernel. `fc1_fc2_fuse_sched.py` imports it plus scalar/peer utilities. Those files are reusable scheduling infrastructure, although the FC1/FC2 readiness policy is part of the W4A16 algorithm and must remain explicitly owned/understood.
- `SwapABSwigluFp4Fc12SchedExtension` is more specialized: it defines swapped-AB work records, ready peeks and tensor-name mappings. Its `get_gmem_tensor` supports six data/SF operands plus FC1 topk; W4A16 primarily needs `a/b/c` views and readiness fields, while weight scales are handled by its own `_weight_task`. Do not move the full W4A4 extension unchanged behind a supposedly neutral base merely because some mappings are generic. A small W4A16 extension can use the neutral scheduler interfaces and retain the exact required record/peek semantics.
- `nv/contract.py` is pure Python finite-coordinate mapping, with no CUDA or core pipeline import; it is genuinely neutral. `TmemTranspose16x32` is a neutral register/TMEM movement algorithm, but lives inside a large core epilogue module with quantization/router dependencies. A function-level extraction is meaningful; a re-export façade over the entire core module does not improve ownership/import isolation.
- Shared `TopkReduce` imports only Cutlass/CUDA, wire format and constants. Its BF16 branch is independent of W4A4 matrix multiplication. Shared packed-weight preparation and universal transport should not be duplicated merely to eliminate every `nvfp4` string in an import.

## Existing organization and the minimal clean boundary

`moe_ep/kernel_src/README.md` organizes source drops by provenance, keeps `src/` verbatim, and places API/Torch/caching adaptation in `shim/`. `cutedsl_megamoe/VENDOR.md` reiterates that this upstream `src/` is not a place for injected W4A16 files. The current approximately1,560-line kernel and570-line epilogue in `shim/w4a16/` are owned kernel implementation, not thin glue.

The vendored BF16 and MXFP8 Mega siblings are the useful compute precedent: `Sm100MegaMoEBf16Kernel` derives from its own `Sm100SwigluBf16Fc12Kernel`; MXFP8 derives from its own `Sm100SwigluMxfp8Fc12Kernel`. Both compose `TokenInPullTokenBackPush` rather than inherit W4A4 matrix math. Their imports of workspace utilities from the NVFP4 Mega module are a historical coupling to avoid reproducing, not a clean model to copy.

Recommended scope:

1. The user-selected **FlashInfer-owned** sibling precision directory `cutedsl_megamoe/src/moe_nvfp4_w4a16/` records its actual provenance and derived BSD code. Do not describe it as a verbatim upstream drop or invent an upstream revision. It contains W4A16 kernel/epilogue/CLC/dynamic BF16 code; the thin `shim/w4a16.py` owns Torch/config/compile/launch plumbing. Preserve the existing public API through package exports.
2. Own W4A16 constructor, workspace regions/views, symbol naming, role/barrier constants and BF16 epilogue paths explicitly. Keep actual launch/decode/MMA/control sequence unchanged; exactly2 decode WGs and current raw/decoded/activation ring policies remain. No operand-sharing, early-raw-release, scheduling remedy or performance tuning belongs in this cleanup.
3. Retain genuinely universal transport, flag tracking, symmetric heap, mapping/math and post-FC2 reducer through a small explicit shared access boundary. Do not copy the approximately4,000-line transport or approximately3,200-line quantized epilogue. Extract the specific neutral transpose/context/byte-region pieces only where their current module import pulls the core pipeline.
4. Treat the fused scheduler extension as an explicit ownership decision: neutral ring/record infrastructure can be shared; W4A16's phase mapping, K-count, readiness and completion policy must not secretly depend on W4A4's specialized core class. Root should keep these semantics visible during constructor/workspace cleanup.

## Exact epilogue work needed

The existing W4A16 `run`, FC1 `_swiglu_act`/`__call__`/`_run_fc1_bf16_subtile`, and FC2 `__call__`/`_run_last_subtile` are already owned. Preserve their arithmetic association, alpha/clamp order, accumulator fences/releases, CLC completion-before-next ordering and non-CLC batching exactly.

Needed from current bases (own narrowly):

- **Epilogue configuration:** geometry constants (`_EpilogueWarpCnt=4`, token64, FC1 down64/gate-up128, FC2 hidden128, gate/up interleave16, barrier IDs), actual BF16 fields, two accumulator stages/no overlap, TMEM layout, subtile count, FC2 hidden predicate, clamp and completion batch fields. Initialize directly; no fake FP4 dtype, quantized SF columns, 8KiB epilogue allocation or quantized-only validation.
- **FC1 context:** field delegation; immutable loop-invariant wrapper; `__extract_mlir_values__` returning[] and identity reconstruction; exact `signal_fc1_done` bound/padded feature policy (`nv/epilogue_refactor.py:1307–1343`). No parent FC1 quantization/body/SMEM setup.
- **FC2 context:** corresponding invariant-context wrapper; BF16 STG constructor; exact `signal_fc2_done`, `_make_output_router`, `run_subtile` (`:1925–2073,2205–2246`). No inherited `SwapABFc2Epilogue`.
- **BF16 FC2 operations:** `fc2_stg_tmem_acc_load`, `fc2_f2fp` with FP32 alpha then BF16 conversion, `fc2_stg_post_f2fp_reorder`, BF16-only `fc2_stg_store_function`, its STG output mapping, BF16/local-or-peer output router, and the small callable bundle if useful to preserve existing call structure. The current factory is `:3126–3148`; its quantized/SF alternatives are unreachable for W4A16.
- **Neutral support:** `Region`, `_TmemTranspose16x32Core`/`TmemTranspose16x32` only (not32x32 overlap variant), optional alpha/topk argument record, needed pure `Contract`/`Space` mapping types. Preserve attribution for derived source.

Do not bring `QuantImpl`, NVFP4/MXFP8 encoders, quantized combine SF routes, UBLK/REDG variants, overlapping-accumulator machinery, or W4A4 FC1 quantization along. A bounded extraction of the actually executed BF16 epilogue is sufficient; a whole-module copy or renaming inherited classes is not.
