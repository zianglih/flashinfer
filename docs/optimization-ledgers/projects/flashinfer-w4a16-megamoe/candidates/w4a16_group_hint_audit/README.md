## Why256 is a reasonable bounded addition

At M256/C2 with I2048, one routed-token cluster tile costs16 FC1 cluster tiles per expert. If32 local experts each occupy one routed-token tile, group512 covers all32 experts whereas256 yields two16-expert groups. This is a source-derived example, not an observed route distribution or a shape-specific selector. If total FC1 work is already below256, both thresholds can produce identical groups; under skew, whole-expert grouping can also make thresholds equivalent.

Earlier FC2 may reduce the interval between producing and consuming a group's activations, and offer a different overlap pattern to the existing producer roles. Conversely it increases group scans, FC1/FC2 transitions and opportunities for FC2 activation waits, and reduces the amount of independent FC1 work available before a dependency. The current NCU metadata-ring and accumulator waits do not prove smaller groups help. The established256 value is a moderate first comparison. If later evidence supports catalog admission, add at most the existing M256/N128/C2/F4/epi and M256/N64/C2/F4/epi dictionaries with group_hint256, keeping epi flags(2,4) and atomic scheduling. Do not double all16 combinations or start a64/None grid.

## Prior evidence and limits

Searches of this effort's ledger/candidate notes and the earlier `flashinfer-w4a16` and `flashinfer-blackwell-megamoe-audit` Markdown evidence found no isolated256-versus512 W4A16 measurement. Shared tuner comments say512 won retained NVFP4/MXFP8 profiles; those different-precision results do not establish a W4A16 rejection. PR4048's split W4A16 kernel has no fused-FC1/FC2 group_hint scheduling axis.

Numerical validation must create and record multiple expert groups under both256 and512, with differing boundaries. Require the realized cumulative FC1 cluster-tile count to exceed512 and inspect the scheduler grouping rather than infer coverage from the global token count. Tiny E8 geometry fixtures may pass without exercising the changed group threshold.

A later go gate is an existing-dictionary256/512 control with fixed geometry/flags/return mode and the same live routing/weights, followed by the existing meaningful numerical/lifecycle checks (zero/partial/odd tails, skew, both return protocols and graph teardown). Native checks must confirm the same640/REG96/two-decode resource contract and no new locals/duplicated MMA; compilation can change allocation even when source storage formulas do not. Only repeated GPU-span evidence across the general sweep, including skew where available, can justify curating an additional tactic. No new public knob or custom per-shape policy is needed.
