# MegaMoE tuning entry-point source audit

The existing NVFP4/MXFP8 path supports a thin W4A16 adapter: a dtype-specific candidate list and launch closure can use the existing collective tuner, and an optional backend-specific offline module can use the shared sweep helpers. Every future W4A16 tactic must retain **two dequantization warpgroups**. No group-count sweep is recommended.

This is a CPU source audit, with no code edits or GPU work. Repository HEAD was `fe4f8132439df1b812f77279e7d033a5128f1ed4`, with dirty W4A16 overlays; exact audited file hashes are in `MEGAMOE_TUNING_ENTRYPOINT_AUDIT_001.json`. Paths below are repository-relative under `flashinfer/` at the effort root. Generic collective timing implementation and benchmark integration are covered by the parent audit.

## Existing entry points

- `flashinfer/moe_ep/tune.py:44` parses the offline CLI; line 50 currently accepts NVFP4 and the two MXFP8 kinds, and lines 129–143 dispatch to backend-local `tuner.py`. The public intermediate argument is post-SwiGLU width (lines 27–30, 53–58).
- `flashinfer/moe_ep/backends/mega/kernel/sm100/nvfp4_nvfp4_bf16_cutedsl/tuner.py:17` creates one symmetric session, enumerates NVFP4 candidates, optionally expands a schedule-only base, calls `finish_sweep`, and destroys the session in `finally`. Its entry at line 89 delegates to shared `run_tuning`. The MXFP8 counterpart has the same structure at `.../mxfp8_mxfp8_bf16_cutedsl/tuner.py:17` and line 87.
- NVFP4 passes `2 * args.intermediate` into both dummy creation and cache resolution (`nvfp4.../tuner.py:39,62`); MXFP8 passes the post-SwiGLU width (`mxfp8.../tuner.py:38,60`). The corresponding backend allocations use exactly the same conventions (`nvfp4.../backend.py:131`, `mxfp8.../backend.py:134`). A W4A16 adapter must use its own frontend's post-SwiGLU width consistently when recording and resolving its `dtype="w4a16"` key.
- Live-input adapters are `flashinfer/moe_ep/kernel_src/cutedsl_megamoe/shim/autotune.py:216` and `:292`: capture the existing session frontend, construct a closure that invokes the dtype wrapper with `sync=True`, derive session-compatible candidates, and record the winning dict on rank 0. Their public arguments are `(y, transformed_l1, transformed_l2, symm_buffer, *, num_tokens, clamps, candidates, warmup_iters, timed_iters)`.
- Backend config `knobs` supports a dict, `None`, or `"auto"` (`nvfp4.../config.py:42–48`, `mxfp8.../config.py:31–37`). Backend construction marks auto tuning pending; first `compute` invokes the adapter and clears pending only after success (`nvfp4.../backend.py:245–261`, MXFP8 lines 241–257). Auto-tuned sessions deliberately disable workspace pooling (`nvfp4.../backend.py:321–326`, MXFP8 lines 273–278).

## Actual candidate grids and restrictions

All curated grids start from cluster `(2,1,1)`, group hint 512, epilogue flag batch `(2,4)`, and atomic scheduling (`shim/autotune.py:43–49`). CPU extraction of the actual pure enumeration functions confirmed these counts:

| Grid | Axes | Count |
| --- | --- | --- |
| NVFP4, BF16 combine | Tiles `(256,128,256)` / `(256,256,256)`; flag 4 / 8; epi / standalone / reused-dispatch token return; optional FC2 reduction | 24 with reduction allowed, 12 without |
| NVFP4, quantized combine | Same two tiles and flags; reused-dispatch only; no in-kernel FC2 reduction | 4 |
| MXFP8 | Fixed `(256,256,128)` tile; flag 4 / 8; epi / reused-dispatch token return | 4 without in-kernel reduction, 2 with it |
| Schedule-only overlay | Existing base plus static / atomic scheduling and group hint `None` / 128 / 256 / 512 | 8 |

NVFP4 enumeration is `shim/autotune.py:52–84`; MXFP8 is lines 87–112. The CLI excludes nondeterministic candidates by default (`moe_ep/tune.py:78–80`). NVFP4's live-input adapter permits reduction only when the session applies routing weights in FC1 (`autotune.py:252–259`). MXFP8 collapses both dispatch-return names to one Boolean and disallows dispatch return together with in-kernel reduction (`shim/mxfp8.py:107–118`; `shim/tuner.py:303–314`). Schedule-only expansion is `backends/mega/kernel/tuning.py:61–68`.

The generic correctness/performance Cartesian space is broader than these curated grids (`shim/tuner.py:37–71,269–289`). Its shared `is_valid` only checks combine/store compatibility and even cluster M for M256 (`:219–250`); it is not a W4A16 geometry validator. `with_knobs` silently drops fields missing from the config, translates MXFP8 token-return names, and infers two-CTA instructions from M256 unless explicitly supplied (`:292–314`). Therefore unsupported stage/group keys can appear in a requested dict without changing the kernel; a W4A16 candidate filter must exclude them instead of treating them as measured axes.

Neither curated tuner exposes raw, decoded, or accumulator stage counts. Only `num_sched_stages` exists in the frontend configs (`shim/nvfp4.py:92–110`, `shim/mxfp8.py:59–73`). NVFP4 derives its AB+scale stages from remaining shared memory and fixes two accumulator stages (`src/moe_nvfp4_swapab/kernel_fc12.py:501–563`); MXFP8 derives A/B stages similarly and may add one B stage when spare memory permits (`src/moe_mxfp8_glu/kernel_mxfp8_glu_fc12.py:511–576`). These are blockscaled operand pipelines, not W4A16's explicit software-dequantization pipeline.

## Defaults and distinct caches

- Factory precedence is explicit dict, otherwise persistent-cache lookup, otherwise dtype heuristic: NVFP4 `shim/nvfp4.py:1063–1107`; MXFP8 `shim/mxfp8.py:853–869`. Correctness-owned reduction settings are reconciled separately (`nvfp4.py:1108–1113`, `mxfp8.py:870–900`). Do not borrow NVFP4's larger-token defaults or reduction choices for W4A16.
- Persistent keys contain device name, dtype, EP size, hidden width, intermediate width, expert count, top-k, and combine dtype (`shim/knob_cache.py:47–57`). Capacity uses the smallest recorded bucket at or above the request, otherwise the largest smaller bucket (`:152–166`). `record_knobs` stores the chosen tile/scheduling dict as the value (`:169–207`); `resolve_knobs` applies dtype-specific fallback (`:258–273`). Source hash, live token count, skew, stage rule, and warpgroup count are absent from this key. Use a dedicated experiment cache file while source/stage rules change; the existing CLI already documents separate files for live-token tuning (`moe_ep/tune.py:88–96`).
- Frontend compile keys include actual geometry, scheduler fields, flags, reduction mode, and clamp (`shim/nvfp4.py:418–445`, `shim/mxfp8.py:343–368`). Applying changed knobs frees compiled workspaces and invalidates the compile (`nvfp4.py:254–268`, `mxfp8.py:194–210`). Backend workspace pool keys also include the configured knob dict and correctness fields (`nvfp4.../backend.py:332–350`, MXFP8 lines 284–299).
- The current W4A16 factory uses `default_knobs` directly when `knobs is None` and bypasses defaults even for an explicit empty dict (`shim/w4a16/frontend.py:509–532`). Thus adding a tuning writer alone would not make W4A16 consume stored winners. The insertion point is this factory, retaining explicit-dict precedence and correctness constraints.

## Thin W4A16 recommendation

1. Define a small `w4a16_candidates` list restricted to validated geometry tuples, two dequantization warpgroups, BF16 dispatch/combine/output, and post-FC2 FP32 routing weights. The current config accepts M128/M256 × N64/N128 × K256, cluster `(2,1,1)`, and ties one/two-CTA instructions to M128/M256 (`shim/w4a16/frontend.py:52–94`). It rejects standalone token return and both FC1 routing-weight application and in-kernel FC2 reduction. The accepted geometry set is not itself a claim that every candidate has performance or numerical evidence.
2. Reuse `autotune_knobs(frontend, launch, candidates, ...)` through a W4A16 wrapper matching the existing NVFP4/MXFP8 adapters. The current W4A16 frontend already has `apply_knobs` (`frontend.py:138–155`), and its public wrapper accepts `sync=True` (`:559–611`). Use that full wrapper so the post-FC2 routing reduction is included; `w4a16_mega_launch_thunk` at line 614 invokes only the frontend launch and does not include the separate `reduce_topk` call at line 609.
3. Keep group count fixed at the existing kernel assignment `num_transform_warpgroups = 2` (`shim/w4a16/kernel.py:178–182`). Preserve fitter-selected raw depth (`:323–338`). The currently inspected overlay derives three decoded stages for N64 and two for N128 (`:101–114`), rather than exposing a stage knob. Do not invent a raw/stage/group candidate key that `with_knobs` will silently drop. If a later task explicitly exposes a stage field, include it in validation and all relevant compile/cache identities before tuning it.
4. Start with the selected geometry/control profile and a bounded flag/token-return or schedule grid; avoid the generic correctness Cartesian product. Existing `schedule_candidates(base)` can be reused directly after a W4A16-specific validity check. A future offline `.../bf16_nvfp4_bf16_cutedsl/tuner.py` can follow the existing small backend adapters, using W4A16's own BF16-input/NVFP4-weight construction; NVFP4 and MXFP8 dummy factories quantize activations (`shim/nvfp4.py:1514–1549`, `shim/mxfp8.py:1230–1259`) and cannot be reused unchanged.
5. For persistent winners, use `dtype="w4a16"`, `combine_dtype="bf16"`, and the existing W4A16 capacity/shape convention consistently. Add cache resolution at the W4A16 factory and public exports alongside the existing lazy W4A16 export lists (`shim/__init__.py:156–170`, package `__init__.py:102–117`). Adding offline CLI support is independent of an online `knobs="auto"` backend extension; the W4A16 public config currently accepts only dict/None (`.../bf16_nvfp4_bf16_cutedsl/config.py:20`).

No patch is proposed or applied. Runtime timing quality and integration choices remain with the parent and integration agents.
