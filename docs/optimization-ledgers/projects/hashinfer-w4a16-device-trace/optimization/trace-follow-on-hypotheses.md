# Follow-on hypotheses after initial pilots

Source review only, 2026-09-25. No GPU work and no repository changes. Parent reports full K256 predecode substantially slower and store16 approximately flat in the ongoing pilot; this note does not independently validate those timings.

1. **FC1 fragment128→64, keep FC2 fragment32.** `_fit_raw_stages` passes128 into `_make_mixed`; FC2 independently passes32. Reducing only FC1's requested fragment changes the size of each register decode batch and its scale/packed-weight lifetime, with unchanged raw/decoded storage layouts, element ownership, ring depths, total conversions, CTA/register allocation, and mathematical output. This is a one-literal, general FC1 scheduling experiment, not another predecode-before-acquire change. Rank2 trace shows decoder completion controls MMA readiness, but does not predict whether smaller batches improve compiler scheduling. Compare actual native code first: register moves, local stack/spills, conversion scheduling, and TMEM store grouping.

   Historical boundary: [CUDA130 decode resource audit](/Users/ziangli/playground/projects/flashinfer-w4a16-megamoe/candidates/w4a16_cuda130/DECODE_RESOURCE_AUDIT.md:49) proposed this same FC1 cap64 only as a conditional experiment. Searches of the effort ledger and candidate READMEs found no measured isolated cap64 result. That is a search outcome, not proof no experiment ever existed. The [transform acquisition audit](/Users/ziangli/playground/projects/flashinfer-w4a16-megamoe/candidates/w4a16_transform_acquire_audit/README.md:40) documents prior rejected full decode hoists, fragment lookahead and per-fragment stores. FC2 fragment64→32 was retained, fragment32→16 rejected; keep FC2 unchanged.

2. **Lower priority: warp-aggregate decoded-full arrivals.** Current transform pipeline producer group counts `32*8*2 = 512` threads; each participating thread arrives on the leader CTA's full barrier after its TMEM-store fence. A consistently counted16-warp scheme with one elected arrival per warp could reduce barrier work without changing any operand completion ring. This needs an explicit warp-wide ordering proof (and potentially `sync_warp` before the elected arrival), exact arrival count changes, both C1/C2 geometry consideration if generalized, numerical/synchronization validation, and native inspection. Extra warp synchronization may outweigh savings; hardware may already coalesce the all-lane arrival. No measured prior matching aggregation trial was found in the ledger. Do not implement casually as a cleanup.

No recommendation to alter global register allocation, reduce the required two transform warpgroups, couple decoded/activation rings, enlarge raw rings without starvation evidence, or repeat FC2 fragment16. Full K predecode and no-peek change ordering in different ways; preserve their separate results.
