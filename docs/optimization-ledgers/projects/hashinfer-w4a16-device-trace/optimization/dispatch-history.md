# Prior dispatch/startup optimization evidence

Read-only historical audit for the PR #13 trace-guided follow-up, 2026-09-25. Current effort source pin: `002ef1454cbacde09972ed5e2ec7dcfe37e55749`. Historical source pins below are **not** claims about that commit's ancestry or exact current implementation. No historical checkout was changed and no GPU run was made for this audit.

The requested window is useful work **while ranks are still waiting for count exchange to complete**, inside `dispatch_exchange_counts_sync`. Most earlier candidates addressed a different window: allowing compute to proceed **after counts were published but before activation payloads were ready**. The closest count-independent startup candidate, early first-ID broadcast, was implemented and measured but not retained. It deliberately left expert decoding after count publication.

## Findings that matter for the next experiment

1. Claiming/broadcasting a linear scheduler ID is not identifying its expert. Historical decoding needed globally valid expert counts, including padding and empty-expert decisions. Moving the scheduler gate alone is not a valid way to start exact weight/decode work during unfinished count exchange.
2. Metadata-first staging, cheaper whole-rank publication, per-row readiness and per-source-CTA readiness were all implemented and measured. None earned retention. They should not be described as untried proposals.
3. Those trials did **not** record the requested causal boundaries—first useful weight load, first dequantization, and first MMA. They reject their measured implementations, not every way of exposing useful work in the new trace's wait window.
4. Existing weight/decode runahead already overlapped remote activation pulls after metadata publication. A change must advance exposed work or first MMA, rather than merely advance work already hidden by pulling.
5. The historical experiments used a different workload and measurement protocol. Their ratios are evidence about those implementations, not predicted EP4/GLM5/256-tokens-per-rank speedups.

## Constraints to carry into the current experiment

- **Separate the windows.** Distinguish local count/routing production, global count publication/peer waiting, scheduler release, source-payload publication, remote pulls, and local received-pool readiness. A combined marker can include active production and actual waiting; only current-source/trace evidence can identify the exposed portion.
- **Count-independent setup versus useful work.** Early linear-ID transport needs initialized cluster barriers but not counts. Exact expert mapping historically needs counts. Useful weight/decode before count completion therefore needs a justified earlier metadata contract or speculation/matching protocol, not merely moving `gen_next_work` above its gate. A deterministic uniform benchmark fixture does not authorize assuming uniform routing in production.
- **Source publication is distinct from received-pool readiness.** The FC1 ready counter protects the local received pool. Remote TMA reads from source staging occur before that local counter is published, so the existing activation wait cannot replace a source-payload release/acquire edge. The extra-publication variants explicitly paid for this missing edge.
- **Preserve dispatch progress.** Compute may fill raw/decoded rings and stall; dispatch must remain able to publish/copy/pull without waiting for that compute to finish. Existing decoded capacity is only three K256 stages at N64 or two at N128, not an expert's full K range. Deeper scheduler queues alone do not add weight/decode storage.
- **Initialization synchronization is not automatically payload visibility.** Historical bootstrap review found that relaxed cluster arrival plus mbarrier-init fencing does not publish ordinary input stores. Preserve actual writer proxy fences, producer participation, and release/acquire handoffs. Routing-ID ownership matters because preparation consumes IDs before the first grid barrier.
- **Preserve lifetime edge cases.** Empty/prestaged ranks, heterogeneous CTA counts, queued/graph invocations, NVLink phase counters, receive-counter bank snapshots/clears/flips, and the NCU replay publication cycle were real design obligations in prior prototypes. Performance runs do not establish all of them.
- **Measure advancement, then cost.** Current traces can resolve the missing causal question: whether earlier work advances first useful weight/decode or first MMA while count exchange truly remains pending. Retention still needs matched uninstrumented full-forward timing. Use fixed tactics for attribution and native AUTO policy for retained behavior; do not reuse historical EP8/H7168/cold-L2 numbers as the current EP4/H6144 result.

The strongest historical conclusion is narrow: straightforward early-ID broadcast and several ways of separating metadata from activation staging did not improve their full-forward controls. The new trace's genuine count-wait interval remains worth examining, provided the next candidate names precisely what becomes runnable before counts and how it preserves the metadata/publication contract.
