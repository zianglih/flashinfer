# Deterministic ordinary finalize: bounded follow-up audit

Source inspected at retainedb90; no production edits or GPU work for this audit. Ordinary means BF16 expert scratch followed by the existing ordered FP32 router-weighted accumulation. It does not mean FP32 scratch. Candidate005's atom is `CopyBulkTensorTileS2GOp` (`moe_w4a16_kernel.py:753–759`), used through `cute.copy` at the ordinary store site `:2268–2276`. `blk_reduce_bf16` at `:2238` is inside `const_expr(self.use_fused_finalize)` and excluded. No TMA reduction is proposed for ordinary finalization.

## Ranked next opportunities

1. **Unroll the existing ordinary epilogue subtile loop.** Held006 is now under `../nonfused_epilogue_unroll/`; one keyword at kernel2119, no body or output-order changes. Full instruction offsets and the last-load release check can become constants for N64/128's2/4 subtiles. Current ordinary N16/32 winners have one subtile, so expect little or no effect there. This is the smallest next trial. It may increase static code size; actual native and full timing must decide.

2. **Potentially skip wholly invalid route subtiles, after a complete work-metadata proof.** Kernel2114–2127 currently loads all TMEM subtiles, including the suffix that the route predicate at2291–2303 prevents from storing. For N128 with33 valid routes, four32-route TMEM fragments are read although only two contain valid outputs. A later ordinary-only loop-bound variant could use `min(full_subtile_count, ceil(valid_routes/epiN))`, keeping the final partial fragment and its original predicates. This preserves each output element's arithmetic and top-k order, but moves the existing accumulator release to the last *useful* TMEM load. It therefore needs explicit proof that every admitted work record has positive valid_routes, and that all participating epilogue warps still execute exactly one fence/release/advance; the validity helper itself only checks group index. Scheduler publication at1239–1250/1296–1310/1348–1364 obtains valid_routes from routing metadata. Do not implement a zero-iteration loop before tracing that routing producer. This is a separate scheduling change, not part of006, and has higher proof cost.

3. **Lower-priority shared-reducer top-k specialization.** `moeUtils.cu:159–204` already uses one256-thread block per token,128-bit vector loads/stores (`uint4`,8BF16), and eight private FP32 accumulators per vector. The remaining top-k loop and expanded-index multiplication are runtime at181–195. A small static top-k dispatcher (for selected common values with the current dynamic fallback) could use the same kernel body, ascending k order, masks and FP32 expression. Established repository precedent is `communicationKernels/moeAlltoAllKernels.cu:105–165`'s `SWITCH_TOP_K` and its templated loops. No parallel reduction, warp shuffles, shared cache, widened block, or reordered summation is needed. However, this touches shared C++ code across dtypes and adds compiled variants; sparse EP workloads may pay code-size cost without benefit. The prior private Triton reducer already combined static top-k with other changes and was rejected for EP8, so this is only an isolated C++ pattern hypothesis, not a newly proven technique. Native inspection must confirm the FP32 dependency chain and control reduction before a trial.

## Findings that do not justify another change

- Vectorization is already128bits (`ElemCopyType=uint4` at `moeUtils.cu:32`, accesses at191/204). There is no scalar-memory copy problem established by source.
- `hidden_size / kElemPerCopy` at167 divides by a compile-time power of two. It is not a dynamic-divisor target. Keep64-bit row pointer offsets; reducing their width would narrow the current large-tensor contract.
- `input_is_expanded` at189 is a uniform runtime choice. Specializing it is conceivable but removes little work while duplicating more shared variants; no emitted bottleneck was found here.
- Python `moe_unpermute` at `moe_utils.py:255–324` already reuses the cached JIT module. Host dtype/function lookup is outside graph replay; it does not explain the captured GPU-chain latency.
- The post-unpermute fill kernel in older profiles was benchmark cold-L2 flushing, not an extra MoE output operation to fuse.

## Explicit historical exclusions

The previous project's `w4a16_optimization_experiments.md:3864–3992` rejects the private Triton deterministic reducer as a universal improvement, block-wide metadata caching, and unconditional512/1024-thread or token-count launch policies. The matched EP8 Triton result was slower despite isolated apparent gains; shared metadata caching added a barrier and broader regressions. These are not proposed again. The same ledger's deferred-store/raw-release trials and current project's rejected003 remain distinct from the single-loop hint. Bounded searches of both ledgers found no explicit ordinary epilogue-subtile unrolling or invalid-subtile loop-bound trial.
