# Pipeline initialization fence consolidation

Retained and pushed as `9c9ed58a2f592577b6652ced00aed383f17f885c`, against `9b4721b0`. The completed independent review copy was removed after source verification. This does not include the rejected TMEM startup experiments or shared scheduling policy.

The operand and accumulator custom pipeline constructors currently fence initialization separately, and the kernel fences again after initializing scheduler and scale-readiness barriers. Add the existing `defer_sync=False` API convention to these two constructors, select it only in the blockscaled kernel, and issue one unconditional fence at the common initialization boundary. Other callers retain their original default behavior. Existing cluster and TMEM rendezvous, PDL, scheduling, pipeline geometry, arithmetic and teardown remain unchanged.

The assembler differential uses the exact installed `ptxas` 13.3.73 and reproduces original clean-control SASS. Removing only the first two explicit initialization fences eliminates two executed startup NOPs for the one-CTA sample. The two-CTA sample loses one startup fence, one branch and three NOPs. Further static-site reductions are trailing alignment padding. Both samples have identical opcode/operand streams after the first TMEM allocation operation, modulo relocated branch targets, with unchanged registers, storage and spills. This is compiler evidence, not an end-to-end speedup measurement; see `ptxas-differential.json` and `startup-summary.json`.
