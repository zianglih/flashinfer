# Owner-loop compile follow-up

Frozen patch `5da2bd3f6217a3b72d17fedadaf61214279e632c6f84135657070fbe1ccb2c5e` fails CuTe DSL4.7.1 IR verification before the first candidate core. The exact log is `gate/diagnostic-v2.log`. Control completed 64 replays and 32 core compilations; there is no candidate runtime or codegen success yet. This supplements, without replacing, the frozen source protocol review.

The failing `scf.yield` starts with a shared `i32` tensor of shape `(4,1)` and alignment8, matching `sInfo`, followed by other captured shared-pointer/MMA/state values. The verifier says the yielded definition is in a child region. Exact SDK `elect_one` constructs a raw resultless `scf.IfOp` context manager. The strongest source-based hypothesis is that the transformed dynamic loop threads captured objects through an enclosing transformed role branch while its definitions remain under that raw elected region. No Python-visible post-loop use was intended; this does not imply the emitted IR has valid scope. The new `producer_acquire` has only a resultless `if_generate` and raw barrier operations, making it a less likely source of this particular multi-object yield.

Parent/implementation owner will try an ordinary DSL-transformed `if tidx % 32 == 0` inside the dedicated scheduler-warp branch. This keeps all owner state in an AST-aware condition and avoids adding a new helper interface. Its correctness condition is one executing thread per CTA, with only CTA0 issuing the multicast request; the existing loop contains no hidden warp collective. Counts/phases and response fencing remain unchanged, and the delayed PDL wait must stay after lane reconvergence. Successful compilation and the planned exact/codegen gate are still required; the scope diagnosis is not yet proven by an IR dump/fix.

The fixed-owner selection is legal at the ISA level. NVIDIA's [PTX try_cancel example](https://docs.nvidia.com/cuda/parallel-thread-execution/#parallel-synchronization-and-communication-instructions-clusterlaunchcontrol-try-cancel) explicitly selects thread0 per CTA for local expectation, then CTA0 for multicast request, without `elect.sync`. The [CUDA guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cluster-launch-control.html) recommends `invoke_one` for compiler peeling-loop optimization; it does not turn dynamic election into a raw-ISA correctness requirement. Our scheduler warp has a live lane0 and does not require CTA thread0 specifically.

No source changes or GPU work were performed for this independent follow-up.
