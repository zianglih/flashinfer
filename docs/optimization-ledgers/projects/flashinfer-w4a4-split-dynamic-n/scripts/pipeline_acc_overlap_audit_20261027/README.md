# N256 FC1 accumulator overlap audit

**N256 FC1 already uses partial accumulator overlap.** `acc_stages=1` describes the pipeline ring, not absence of MMA/epilogue overlap. This is confirmed by the saved K3 native all-CLC compiled-kernel receipt: N256, K256, two CTA, five operand stages, one accumulator stage, `overlap_acc=True`, one metadata slot. The old published N128/K512 FC1 instead has two full accumulator stages. Current retained source reviewed: `9b4721b0`.

The FC1 wrapper passes `overlap_activation_accumulators=None` (wrapper:985), so the core derives it from capacity (core:408,447). At N256/M256/K256 NVFP4, each CTA has 256 accumulator columns plus 48 scale columns. Two full accumulators would require 560 columns, beyond the 512-column capacity. The implementation instead reserves two windows `[0,256)` and `[192,448)`, with scales in `[448,496)`. Their shared 64-column interval is consumed first: two 32-token slabs, reverse or forward according to phase (utils:722–818). Then the accumulator barrier is released and MMA can overwrite that interval while the epilogue processes the remaining six slabs. No extra transpose is introduced by this overlap.

`bulk_tokens` only selects the FC2 shared-memory/bulk-store path. It is zero for FC1 and does not disable FC1's independently derived overlapping activation path. SiTU, SwiGLU, GeGLU, per-token scaling and generated output scales all use the same overlap ordering. Moving the release ahead of activation/transposition would be unsafe because the current epilogue uses the shared accumulator interval as TMEM transpose scratch.

One possible future co-design opportunity is to finish the protected prefix's TMEM work before its output quantization/stores. Currently the first protected slab performs absmax/quantization/store before the second slab is read and transposed; only then is ownership released. Buffering the first transformed slab in registers could defer that non-TMEM work until after release, preserving arithmetic and the existing number of transposes. It requires extra live values (16 additional FP32 values per lane for one gated slab, before compiler register allocation) and has not been implemented or measured. It should use the already derived `overlap_activation_steps`, not add a tactic axis or model/dtype rule.

The current global 64-column overlap cap is also conservative for FC1's generic slab loop, but it is a real FC2 ownership limit: FC2 bulk releases after exactly 64 columns. Do not relax the shared cap blindly. A larger-SF FC1 geometry would need matching allocation/release proofs and separate validation; this does not offer a missing switch for the currently selected K3 K256 case.

`receipt.json` records current file hashes, precise code locations, the existing selected-kernel receipt/hash, and a pure-host proof that both phase traversal orders read the shared interval before release. No source edits, new tests, GPU work or performance claim were made. The 180-tactic/no-additional-axis constraint is unchanged.
