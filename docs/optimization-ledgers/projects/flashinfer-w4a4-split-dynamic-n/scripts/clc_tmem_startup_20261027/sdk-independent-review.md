# Independent SDK TMEM rendezvous review

Source-only review of the exact installed CuTe DSL4.7.1 capture in `../clc_reference_audit_20261026/sdk-TmemAllocator.py`, together with current owner-candidate kernel roles. This confirms the existing `../clc_reference_audit_20261026/cutlass.md` exclusion analysis; no source edits or new GPU checks.

- `allocate` (lines193–231) issues physical allocation only from configured warp0. The remaining operation updates allocator bookkeeping. Keeping this call in common code preserves the allocator state without making the scheduler execute `alloc_tmem`.
- `wait_for_alloc` (234–244) is exactly the configured named barrier's `arrive_and_wait`. It is not an additional hardware allocation-completion primitive. Excluding32 scheduler threads requires reducing this barrier's count from192/320 to160/288 and having every remaining worker thread arrive exactly once.
- `retrieve_ptr` (247–265) reads the shared allocation result and creates the typed pointer without synchronization. Scheduler must bypass both waiting and retrieval. Every real TMEM user must still retrieve after allocation publication; do not rely on dead-code elimination to remove an early invalid shared read or initialize a fake pointer to satisfy branch merging.
- Constructor-side two-CTA deallocation initialization (25–47,129–139) uses allocator warp0,32arrivals and an init fence. Preserve it before the common cluster initialization boundary.
- `free` (339–376) uses only allocator warp0. In two-CTA mode its32threads arrive at the peer deallocation barrier and wait locally before freeing. This is independent of the retrieve named barrier; scheduler is not a participant. Preserve the final all-thread CTA join,128-thread freeing-role barrier and existing deallocation handshake.

**Blocking caveat for a naive skip:** in one-CTA CLC, the retrieve barrier is currently the first CTA-wide rendezvous after deferred info/CLC barrier initialization. A fence alone does not force scheduler arrival after warp0 initialization. In particular, this repository's `custom_pipeline.pipeline_init_wait` only emits `mbarrier_init_fence`, despite its broader docstring. It cannot replace the missing rendezvous. Use an actual common CTA initialization join before physical allocation for this case; the existing two-CTA cluster arrive/wait already provides the required join and must remain.

The minimal safe separation preserves common pipeline/allocator construction and initialization, then permits scheduler to bypass TMEM readiness while all160/288workers retain wait/retrieve. It must not introduce a new early routing read: existing PDL routing-release conditions still govern scheduler startup, and delayed payload wait remains outside the owner election. The helper/role structure must keep the typed pointer scoped to actual worker users and final freeing users, without exporting an undefined branch value. Actual CuTe compilation, barrier count/participation codegen, exact changing-route replay and a bounded startup/performance diagnostic remain necessary before retention.
