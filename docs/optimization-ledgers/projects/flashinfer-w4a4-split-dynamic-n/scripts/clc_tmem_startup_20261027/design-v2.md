# TMEM startup V2 protocol proposal

Build on clean `9b4721b0` in the same active review copy. Preserve the neutral V1 (`be8a12bb`) source/evidence before editing. No host tactics, scheduler protocol, dtype policy, arithmetic, PDL ordering, allocation/free ownership, or model dimensions change.

**Wait only in the five TMEM reader warps:** four epilogue warps plus the MMA warp. For inline epilogues, the first four producer warps also own the epilogue, so they wait/retrieve at the beginning of their existing branch. For overlapped epilogues, only dedicated epilogue warps4–7 and MMA warp8 wait/retrieve. The producer warps and scheduler do not wait for TMEM. Keep the three existing role-local pointer declarations and final free retrieval from V1; place the shared named barrier’s `wait_unaligned()` immediately before each role-local retrieval and remove the common wait predicate.

**Allocator publication still participates.** Allocation is executed by warp0 and writes the holding buffer. The SDK pointer retrieval has no synchronization. In overlap mode warp0 is not a reader, so excluding it from barrier3 entirely would be a race even if all160reader threads arrive. After common `tmem.allocate(...)`, allocator warp0 performs one nonblocking arrival on the same named barrier, only under compile-time `overlap_epilogue`. It then continues its startup/prefetch work without waiting. Inline warp0 participates exactly once via the reader-role wait; it must not also arrive in the common allocation section.

| Roles | Nonblocking publication arrivals | Waiting reader arrivals | Barrier3 count |
|---|---:|---:|---:|
| Inline epilogue | 0 | 4×32 epilogue +1×32 MMA | 160 |
| Overlapped epilogue | 1×32 allocator | 4×32 epilogue +1×32 MMA | 192 |

Express the count as fixed ownership: `32 * (4 + 1 + int(self.overlap_epilogue))`, with a short comment naming the four epilogue warps, one MMA warp and separate allocator warp under overlap. Store the `NamedBarrier` as a local `tmem_ready` object, pass it to the allocator, and reuse it for the nonblocking arrival. This avoids reaching into private allocator state. The count is independent of scheduler, CTA group, dtype, shape or tactics. Barrier3 is used for this one startup phase only.

**Initialization precedes all divergent roles.** Keep the common initialization fence and two-CTA relaxed cluster arrival. Call the exact SDK `pipeline.pipeline_init_wait(cluster_layout)` unconditionally before common allocation: one-CTA kernels use the full-CTA barrier0, including static one-CTA; two-CTA kernels retain their existing cluster wait. This establishes initialization completion before producers/scheduler can bypass TMEM. The newly necessary static one-CTA join is explicit; it must not be replaced by the similarly named repository helper that only fences.

**Ordering and teardown.** Allocation bookkeeping remains common. Each consumer's barrier3 wait now follows the existing startup prefetch/PDL code but immediately precedes its first pointer read. Allocator publication occurs earlier, directly after allocation. Prefetch and scheduler operations do not consume TMEM; their existing operand/metadata barriers protect any data they share with MMA. PDL gates/signals and dependency checks stay at their current locations. The final full-CTA barrier1,128-thread relinquish/free barrier2 and independent two-CTA free handshake remain unchanged. All consumer arrivals occur even for empty/padded routes, before role loops, so zero work cannot omit an arrival.

**Exact SDK evidence.** `sdk-TmemAllocator.py` in the neighboring reference audit proves warp0 allocation, named-barrier-only wait, unsynchronized shared pointer retrieval and allocator-owned free. `named-barrier-capture.json` / `sdk-NamedBarrier.py` pin installed CuTe DSL4.7.1. Use `NamedBarrier.arrive_unaligned()` for allocator publication and `wait_unaligned()` for the reader roles. These emit `barrier.arrive` / `barrier.sync` without the aligned convergence promise. The allocator’s `wait_for_alloc()` is only a wrapper around its configured barrier, so calling the same barrier directly preserves its synchronization/bookkeeping contract. The [official PTX barrier specification](https://docs.nvidia.com/cuda/parallel-thread-execution/#parallel-synchronization-and-communication-instructions-bar) permits different warps to mix these operations with the same barrier/count; legacy `bar.arrive`/`bar.sync` imply aligned execution. Explicit unaligned methods match the role-specific call sites. No new SSA value crosses a runtime branch.

**Validation after review:** unchanged eight-case forced-CLC paired replay/codegen gate (four formats,1/2CTA, inline/overlap, FC1/FC2, PDLoff/on, live/empty/padded/terminal routing), plus static one-CTA inline and two-CTA overlap cases. Inspect barrier3 counts160/192, exactly one allocator arrival under overlap, no producer wait/pointer read there, unchanged teardown/geometry, no spills, and added static1CTA init join.
