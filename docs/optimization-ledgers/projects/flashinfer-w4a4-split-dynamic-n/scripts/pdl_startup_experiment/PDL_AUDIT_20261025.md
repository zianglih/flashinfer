## Ordering rules and transitive handoff

[PTX 9.2 / CUDA 13.2.2, §9.7.13.13](https://docs.nvidia.com/cuda/archive/13.2.2/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-griddepcontrol)
defines scheduling after every CTA has triggered or completed. Repeated
triggers in one CTA add no effect. The wait drains prerequisite grids and
their memory operations. A preceding release fence can synchronize with
dependent-grid start: GPU scope requires the same memory synchronization
domain; system scope also covers differing domains.

The [CUDA PDL guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/programmatic-dependent-launch.html)
requires the dependent launch attribute and a dependency wait before reading
producer results. Stream capture preserves the programmatic dependency edge.
Overlap is opportunistic; correctness must also hold with no overlap.

For a sequence route→prep→FC1→FC2→combine, preserve each post-wait trigger
boundary. This ensures earlier producer completion precedes the next
handshake rather than allowing an unchecked cascade of early launches.
Combine's routing reads are a special case: they precede its own output
wait. For a formally explicit relay, use FC2 wait→release fence→trigger,
with routing unchanged thereafter. The fence does **not** publish unfinished
FC2 outputs; combine still waits before loading them. This is a conservative
documented candidate, not a claim of observed corruption in the predecessor.
`common/kernel_utils.py:333–360` currently emits bare wait/trigger assembly,
with no implicit release fence.

Place an early trigger on a common path reached by every CTA, including
zero-work and partially active CTAs. If using one elected issuer per CTA,
that issuer must itself have completed the predecessor wait. Never put the
only trigger behind a live-tile predicate or a particular expert condition.
No new inter-grid spin protocol is needed.

Reviewed implementation refinement: every thread retains the original wait;
then `if warp == 0` / `elect_one()` contains both the optional FC2 nonfused
release and the only core trigger. This issuer has itself acquired the
prerequisite results. No current-grid peer writes need gathering, so an
extra CTA barrier is unnecessary. Other warps must not retain an outside
trigger that could race ahead of the fenced issuer. Preparation retains its
scheduling-only trigger and no added release. LLVM
`fence(AtomicOrdering.release, syncscope="device")` is the source operation;
the pending compiler gate is emitted `fence.release.gpu` before the trigger.
Candidate pins and actual-module harness review are recorded in
`PDL_REVIEW_bbb04823_a3b0042e.json`.

## Resource and usefulness bounds

- FC1 and FC2 each consume most of an SM's shared memory. At the current
  N16 geometry the measured control FC1 uses197504B (the epilogue candidate
  uses181120B), so two large GEMM CTAs cannot coexist within233472B/SM.
  FC1→FC2 overlap is therefore primarily startup on SMs freed by grid tails,
  not simultaneous full-GEMM CTAs on one SM.
- Combine has no shared allocation and128threads for the target T32/T128
  cases. It can use resources alongside an FC2 CTA; metadata setup can hide
  behind FC2 computation, subject to registers and scheduling.
- Preparation's grid can be2368CTAs on148 B200 SMs (16CTAs/SM at128threads).
  Every CTA must have launched and triggered or exited before its dependent
  becomes eligible. Saturated thread residency and gradual block admission
  may shrink the useful window. Preserve the selected grid; changing it
  would confound the earlier measured grid16 policy.
- A source statement moving layout/constant calculations before the wait
  need not move emitted work. Inspect generated instructions or a bounded
  timeline before attributing performance to a hoist.

## Why not prefetch weight TMA yet

Weights and weight SF are static, but this grouped core needs `expert_idx`
and `num_tiles` to choose the actual address. Those are outputs of routing.
The public low-level core contract does not universally promise they are
ready before its dependency wait. Keep those reads and TMA after the wait
in the first candidate. The host's internal chain could support a later
explicit two-level readiness contract, but that is a separate change.

W4A16 already has that more elaborate separation:
`moe_w4a16_kernel.py:1410–1428` consumes tile-info, waits on activation,
then releases FC2's finalizer; `1474–1503` has a distinct static-weight
producer consuming ready tile-info and can trigger FC1 dependents before
activation readiness. Its tile-info pipeline is the missing proof in a
naive grouped-core weight-load hoist. No W4A16 code change is proposed.
[CUTLASS's model-aware PDL example](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/dependent_kernel_launch.md)
likewise distinguishes weights known independent of the preceding producer
from activations that require the wait.
