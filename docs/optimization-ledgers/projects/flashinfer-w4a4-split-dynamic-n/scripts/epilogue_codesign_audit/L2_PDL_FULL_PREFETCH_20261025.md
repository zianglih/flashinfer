## Bounded variants and closed directions

1. **First isolate streamed SFA on the newly admitted FC2 prefetch path.** Private direct `weight_scale_cache_policy` defaults0; caller selectsFIRST only when startup prefetch is admitted and the existing A policy isFIRST. No wide-weight policy extension, no FC1 policy change, no public API knob, no extra prefetch traffic. This is a fresh causal condition despite W4A16's old SFA-FIRST loss: those scales now arrive while FC1's handoff is live. It remains a measured hypothesis.
2. **Optional consumer B-LAST paired with the same first arm**, if useful to test current regular-TMA reuse. This does not protect FC1 output before FC2 starts reading it; describe it as preserving FC2 activation reuse against continuing weight traffic. Leave SFB normal in the minimal experiment and do not claim a complete protected-handoff tier. B-LAST's old Gather4 results were mixed, so new regular-TMA/full-prefetch measurements must justify it.

A producer-side FC1 payload+SF-LAST experiment would address the prewait handoff more directly, but is wider: ordinary vectorized payload and scalar SF store policies both need implementation and codegen checks. Normal or FIRST consumer access can lower priority but is not a global last-use proof, because output-channel CTAs reuse rows without a globally ordered final consumer. FIRST may hurt that reuse. Don't claim two generations can be protected indefinitely. Prefer the smaller two arms above first.

Do not repeat without new evidence: global wide A-FIRST (regressed), extraSFB fetch-size hints (neutral/slower), blind global weight-line prefetch (W4A16 losses), FC1-store-LAST alone (W4A16 neutral/regressed), or FC2-storeLAST+combine-readFIRST. That last exact project experiment passed numerics but lost fullchain:0.992260× atT4,0.995215× atT16384; wideFC2 was0.956949× (`scripts/pdl_handoff_cache_experiment/README.md`). Full-capacity FC2 startup changes the FC1→FC2 overlap, not that FC2→combine handoff.

## Independent work beforewait

**Next low-overhead candidate:** reuse first-tile livecount/expert/mn_limit/valid and route origin across the static one-CTA FC2 wait. Current warp0 reads livecount/expert beforewait; allroles then reread livecount, producer/epilogue rereadexpert+limit, and MMA rereadslimit. These are already-completed routing ancestors under the explicit publication contract. Move only the first tile's required loads/address arithmetic, keep invalid-work guards, and reuse them instead of adding duplicate prefetch. Every role still waits, and actual B/SFB data remainsafterwait. Pipelined subsequent tiles retain normal metadata loads. Check PTX/SASS movement and register/local-memory resources: source-level CuTe views are often compile-time objects or can be sunk by the compiler, so moving view syntax alone proves nothing.

Alpha is also independent once the expert is known, but has lower priority: it is a single float used by epilogue after MMA, outside first-B issue, and early loading lengthens its live range. Keep routing-scale/mapping arrays and alpha out of the first experiment unless generated code shows a clear critical path. There is no justification yet for new L2-prefetch instructions.

**FC1↔prepare extension is feasible in principle, but deferred.** Prepare already waits for sorting before signaling. To permit FC1 prewait routing reads, prepare must explicitly GPU-release those completed ancestors before its first trigger (same memory domain); current code lacks that release. FC1 must still wait for prepared B/SFB writes. More subtly, current early-stage FC2 mapping assumes a bounded static1D grid. CLC FC1 starts from gridY route index and gridX channel index, may begin on a padded route, and publishes firstwork through the metadata scheduler. A correct extension must prime only the initial live work corresponding to the actual launch coordinates, then skip exactly that work's later A/SFA acquire, preserving queue ownership, acquire-before-cancel, padded-route handling, and one-CTA scheduling. Reusing `block//total_m_tiles` blindly or disabling CLC would change correctness or experiment scope. No production extension is proposed before the simpler metadata result.
