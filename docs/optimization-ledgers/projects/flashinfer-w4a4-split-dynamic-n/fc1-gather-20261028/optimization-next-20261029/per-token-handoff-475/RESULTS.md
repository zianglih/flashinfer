# Per-token FC1 → quantizer → FC2 handoff, retained 475cae6b

The intermediate per-token quantizer is the largest exposed interval in N3U TP8 at16,384 tokens: **~641µs after FC1**, within a1,957µs complete public call. FC2 overlaps only42–43µs with the quantizer tail. This is a concrete optimization target; it is not proof that the quantizer accounts for the historical294µs TRT gap, because no fresh TRT timeline was collected. TRT also writes BF16 after FC1 and runs a standalone per-token quantizer.

## Contracts and meaningful implementation difference

1. **Same benchmark per-token recipe on both backends:** MSE4over6, E4M3 max256, 4over6 error fastmath enabled; base FP4 quantizer fastmath disabled. Initial and intermediate global inverse scale is1/(256×6)=1/1536. Initial quantizer is public`nvfp4_quantize(...per_token_activation=True,backend="cute-dsl",sfLayout=linear)` for both CuTe/TRT. Weights stay standard NVFP4 without4over6, prepared outside the activation-only environment scope. See benchmark lines536–548,625–695,719–722,1180–1240,1245–1305.
2. **CuTe intermediate:** FC1 explicitly chooses BF16 (`quantize_output=False`), then shared `nvfp4_quantize_per_token_cute_dsl` with128×4SF layout and device `valid_rows`/per-tile `row_limits`. `convert_sf_to_mma_layout` only views/permutates tensor metadata and launches no kernel. FC2 consumes both block scales and per-token row scales. See`fused_moe.py:799–865`;`cute_dsl/utils.py:367–450`.
3. **TRT intermediate:** runner chooses BF16 FC1 output when GEMM2 per-token scaling is enabled, then invokes`invokeNvfp4QuantAndPerTokenScale` on`num_tokens*topk` expanded rows with expanded→permuted mapping; the current GEMM2 tactic selects8×4 or128×4SF layout. Recipe determines both global inverse scale and compile-time conversion; FC2 receives `token_scales_fc2`. See`csrc/trtllm_fused_moe_runner.cu:454,752–797`.
4. **CuTe quantizer geometry:** K640 means40real16-element SF blocks per row; the current minimum128-thread CTA loads the last valid block again for88inactive threads, reduces across4warps, then masks quantization stores. At this point the register-resident path reads each owned block once, retains words, and quantizes from registers; replacing it with a second global read is not a sound default. Bounded grid is148×8=1184CTAs, looping through426,752 padded rows;360,448 are live and66,304 holes only zero SF slots. EachCTA handles up to361row iterations and executes an end-of-row CTA barrier. Useful logical BF16 input plus packed output/blockSF/row scales is592.6MB, so641µs is~0.92TB/s of useful logical traffic; this is an arithmetic estimate, not measured HBM traffic. See`nvfp4_quantize.py:848–942,1048–1218,1220–1355,3406–3444`.
5. **TRT quantizer geometry:**128threads as well, but oneCTA per expanded live row; rows map to their permuted output positions, so no iteration through padded holes. CurrentBF16 launcher sets`CACHE_INPUT=false`; it uses32-byte packed loads in each of two passes. The precise4over6 path broadcasts row encoding through global per-token storage with CTA barriers. Thus TRT is not an obvious instruction-minimal oracle; CuTe's register retention is already better in one respect. See`csrc/nv_internal/cpp/kernels/quantization.cu:404–450`;`.../tensorrt_llm/kernels/quantization.cuh:857–1004`.
6. **PDL:** CuTe quantizer waits on ancestors at entry, CTA0 republishes completed ancestors with a GPU fence, then everyCTA signals dependents before processing. This already permits FC2 setup/weight prefetch while quantization proceeds; measured42–43µs overlap confirms exposed startup work, but mostquantizerwork remains on critical path. TRT's explicit quantizer waits at entry and signals at the end. Removing CuTe's entry wait would read FC1 data/metadata before publication; moving the signal alone is unlikely to recover641µs because it is already early. See`nvfp4_quantize.py:1048–1058`;`quantization.cuh:864,1002`.

## Next bounded direction

First collect same-tile/sharedCLC controls. Then inspect quantizer generated instructions and consider a general compile-time row ownership policy derived fromK: avoid redundant last-block loads and cross-warp reduction for inactive lanes; potentially pack multiple independent narrow rows into aCTA so each row uses only the warps needed for its SF blocks. Keep the exact recipe, single input read, device row-limit semantics, and early PDL ancestor-publication contract. Do not add model/dtype-specific branches or another autotune axis. We have not established whether smaller CTAs, multiple rows perCTA, launch geometry, or the padded-row traversal dominates; they require focused control/profiling before implementation.

No combine redesign is proposed: wide256/vector-outer/geometry/metadata/cachehandoff variants were rejected in `optimization-20261028/tp-small-gemm-round/prepare-combine-next-audit/RESULTS.md`, `post-hybrid-polish/prepare-combine-audit/RESULTS.md`, and `warp-polish/epilogue/PROFILING.md`.
