# Read-only FP32 MOVM feasibility

Current full-precision FC1 transpose is not a direct `movmatrix` substitution. [PTX13.2.2 movmatrix](https://docs.nvidia.com/cuda/archive/13.2.2/parallel-thread-execution/index.html#warp-level-matrix-transpose-instruction-movmatrix) supports an8x8 matrix of16-bit fragments and requires converged whole-warp execution. Source/destination figures are saved locally with hashes; `fragment-map.json` checks all64 halfword coordinates.

Under those fragment layouts, the transfer maps lane bits and the halfword bit as `newL=(oldL3,oldL4,oldH,oldL0,oldL1)`, `newH=oldL2` (least-significant first). Native FP32 FC1 ownership instead needs four register-index bits moved into token-owning lane bits while preserving both halfwords of everyFP32 value. Thus simply applying MOVM independently to each original32-bit word scatters its high and low halves; it is not a valid full-value transpose. Additional halfword/register permutations or lane exchanges are required. No lower-cost complete sequence has been derived here; this is not an impossibility claim or benchmark conclusion.

Historical `scripts/epilogue_experiment/build_movm.py` first rounded FC2 values toBF16/FP16, then used32 MOVM operations plus a remaining TMEM store/load pass. That rejected experiment is different from a bit-preserving FP32 replacement. The previously rejected narrow FP32 shuffle epilogue and current shared-FP32 exchange also remain separate evidence. Do not launch a cosmetic rediscovery; derive an exact coordinate sequence and realistic instruction budget first. No repository edit or GPU run was made for this audit.
