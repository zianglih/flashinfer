# FC2 scatter4 independent review

Candidate: `flashinfer-scatter4-review`, based on retained `cb35c42f6143aa08546ee1c6c8d6e6913c6cf03f`; kernel SHA256 `32c2a60ffd0f67108a1c7ecc8d191edbf71934b40d1204c616ca7aae6bc15656`. Read-only source review and CPU layout verification; no GPU launch or sanitizer by this reviewer.

**Compiler gate found a descriptor bug in the initial candidate.** `Swizzle(3,3,3)` produced512 copy bits and a32-element contiguous box. The independent source review incorrectly assumed element-unit swizzle parameters. CuTe DSL uses byte-unit swizzle parameters here: `tcgen05.make_smem_layout_atom(K_SW128, dtype)` uses `Swizzle(3,4,3)`. The epilogue agent confirmed that this one-argument fix produces1024 copy bits and64 elements, and its first standalone copy is exact. Full phase/tail checks are in progress. The CPU physical-address proof below remains valid for the intended128-byte/16-byte-atomic descriptor.

**Scope after that descriptor correction:** This is only the existing BF16/FP16 bulk FC2 epilogue. Expanded output layout, output rounding, combine, scratch capacity, tactics and all synchronization remain unchanged. The source diff changes only the swap-AB kernel file.

- **Descriptor:** Logical output is row-major `(expanded_rows, channels)`. The corrected atom uses `(1,64)` and byte-unit `Swizzle(3,4,3)` for16-bit elements, giving a rank-2 descriptor whose contiguous box dimension is 64 elements/128 bytes and other box dimension is 1. Raw scatter coordinates correctly put the channel first and four output rows next. Raw PTX bypasses generated coordinate validation, so inspect the copy atom's copy bits and tensor basis as well as rank. This requirement caught the initial descriptor bug.
- **Swizzle/alignment:** Existing scratch is 128-byte aligned. Each source is that base plus whole 128-byte rows; no alignment increase or planner change is needed. Applying `address ^ ((address >> 3) & 0x70)` to absolute byte addresses incorporates the nonzero swizzle base phase. Applying the XOR only to offsets would be wrong for seven of eight base phases. `verify_layout.py` checks all eight phases for 32-token/one-stage and 64-token/two-stage cases, proves unique writer/read ownership of every 16-byte chunk, and proves no padding or cross-stage access.
- **Routing/tails:** `copy_row = warp*(tokens//4) + lane*4` partitions all rows exactly once. Metadata group selection and lane shuffles match the previous row ownership for both 32- and 64-token slabs. The CPU proof checks all 1,544 combinations of tile N128/N256, slab32/slab64, forward/reverse traversal and live-token count. Padded rows use the nonnegative sentinel `output.shape[0]`; valid metadata loads are unchanged. Supported output channels are multiples of128, so both64-channel halves are valid whenever the retained CTA/channel guard passes.
- **CTA ownership:** Two-CTA MMA does not imply a cluster-scope store: each CTA stages and scatters its own128-channel slice. Logical M512 repeats the same local epilogue for the next channel tile. Output destinations are disjoint, except deliberately suppressed padding. No new cluster rendezvous is required.
- **Visibility and reuse:** All128 epilogue writers execute the shared async-proxy fence and named barrier6 before any TMA reads. Every thread commits its own bulk group, including empty groups; issuing threads wait for source reads before the128-thread barrier permits stage overwrite. Final `wait_group.read(0)` plus the same barrier protects later epilogue reuse. These waits are necessary: the four issuing warps read data written by both pairs of epilogue warps. Existing accumulator release points, TMEM load fences, scheduler joins and kernel/PDL completion ordering are unchanged. This candidate adds no barrier or quorum.
- **Performance boundary:** 64-token slabs use32 scatter transactions instead of64 one-row transactions (32-token slabs16 instead of32). This alone is not an end-to-end speedup claim. The current lane-dependent issuers can require uniform-register conversion and an active-lane peeling loop; inspect SASS against the old bulk implementation. A single elected lane per warp with an explicit group loop and shuffles outside divergent election is a possible follow-up.

## Primary-source checks

The [PTX tensor access and instruction specification](https://docs.nvidia.com/cuda/parallel-thread-execution/#tensor-tiled-mode-tile-gather4-tile-scatter4) defines rank2 scatter4 with four row coordinates, a one-row bounding box, and ordinary tiled constraints. Its [swizzling description](https://docs.nvidia.com/cuda/parallel-thread-execution/#tensor-swizzling-modes) gives128-byte swizzle phase `(shared_address/128)%8`. The [bulk-group wait contract](https://docs.nvidia.com/cuda/parallel-thread-execution/#data-movement-and-conversion-instructions-cp-async-bulk-wait-group) makes `.read` completion sufficient for source reuse.

The [CUDA13.2.1 asynchronous-copy guide](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/04-special-topics/async-copies.html) permits shared-to-global out-of-bounds tiles with nonnegative starts and requires128-byte shared alignment. It also demonstrates writer fences, a collective join, bulk commit and read-wait before source reuse. The same guide warns about active-lane peeling and recommends elected issue.

Repo precedents: `experimental/qwen_3_5_block/_cudnn_frost/gemm/frost/tile_helpers.py::moe_scatter_row/tma_scatter4` uses the same positive OOB sentinel and coordinate order. `.../frost/tile_dsl/tma.py` documents absolute-address swizzle and uniform TMA issue. CUTLASS `include/cute/arch/copy_sm100_tma.hpp::SM100_TMA_STORE_2D::copy` supplies the same scatter4 instruction form; its epilogue collectives preserve writer fence/join and source-read completion before staging-buffer reuse.
