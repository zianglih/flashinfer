# Independent review: adjacent-warp SF32 barriers

Reviewed `epilogue/candidate.patch` read-only against retained `99f4d0c27`. No source blocker found. The two 64-thread participant groups cover the complete shared-memory dependency graph; no named-barrier-ID conflict is introduced.

`_run_token_group` computes epilogue-relative `warp=(tidx//32)%4`, where callers pass physical `tidx-128`. `_gated_sf32_absmax` writes `shared[warp,lane]` and reads only `shared[warp^1,lane]`. Therefore physical warps4/5 form the first group (scratch rows0/1, barrier6) and warps6/7 form the second (rows2/3, barrier7). The index domains are disjoint for every lane. TMEM transpose scratch is separate from this shared-memory scratch, so its ownership does not add an inter-pair dependency.

The first barrier publishes both rows before either peer reads. The second barrier prevents either peer from overwriting its row for a later token/channel/work item until both have completed the prior read. Both joins are necessary; the patch retains both. The helper call precedes lane-specific live-token and output-channel store predicates. Outer route-slab predicates are CTA-uniform, including partial and zero-token routes. `run_overlapping_fc1` and its forward/reverse channel/tile loops invoke the same helper uniformly, so no pair loses participants.

Different pairs may now advance asynchronously into subsequent helper calls or work tiles, but their rows remain disjoint. Accumulator release continues to require all128 epilogue threads per CTA, including the same TMEM load fences. Early partial release is also unchanged. Consequently one fast pair cannot independently allow MMA to overwrite an accumulator window still used by the other pair. Metadata release still counts all existing consumers before a slot can be overwritten.

The kernel's named barriers are1 for the final256-thread join,3 for TMEM retrieval and6 for epilogue shared exchange/bulk-store joins. No existing barrier7 use exists in this kernel or its TMEM helper. Operand/accumulator/CLC pipeline mbarriers occupy a different barrier resource. Bulk output requires `generate_sfc=False`; `_gated_sf32_absmax` requires `generate_sfc=True`. Thus the bulk path's128-thread barrier6 cannot coexist with the pair6 use in one compiled specialization. The final full-CTA join and two-CTA deallocation handshake still execute after both pairs finish.

Installed CuTe4.8 `NamedBarrier` accepts an `Int32` ID. Hopper FMHA also uses per-warpgroup dynamic IDs (`references/cutlass/examples/python/CuTeDSL/cute/hopper/kernel/attention/fmha.py:1238`). NVIDIA's [CTA-barrier specification](https://docs.nvidia.com/cuda/parallel-thread-execution/#parallel-synchronization-and-communication-instructions-bar) describes barrier synchronization for the participating warps and explicit thread counts; each candidate pair supplies a uniform ID and count64. Generated code should verify that both SF32 sites use the dynamic pair ID and count64, while unaffected kernels retain their original barrier usage. A source ownership proof does not establish a speedup or replace the pending focused runtime checks.
