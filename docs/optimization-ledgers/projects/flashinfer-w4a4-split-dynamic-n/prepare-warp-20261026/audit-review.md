# Preparation warp ownership review

Reviewed the unchanged candidate at parent `0def601d6603df828ea39679b41ccbce64f7f09e`, preparation source SHA256 `eec66151cb112cbcbe1369100407b87ba1cccf132d792fa7dc0c42fbcff9702d`. No source changes were made during this audit.

No new correctness defect was found in the ownership change. The reproducible CPU check is `python3 prepare-warp-20261026/audit_static.py`; its receipt records 320 row/grid combinations, 1024 payload widths and 208 SF-layout combinations.

- **Rows and grid:** `block *4 + warp + iteration * grid *4` enumerates each SF row exactly once. Division by `grid *4` identifies the unique iteration and remainder; the remainder uniquely identifies block and warp. The grid remains positive for positive capacity, is bounded by hardware thread capacity, and includes the full final 128-row SF atom. The proof includes capped grids, partial final work, zero active count, shrinking active count and multiple loop iterations.
- **Payload:** each lane owns eight Uint32 values starting at `(lane + iteration *32) *8`. The existing host/constructor checks guarantee 32-byte aligned bases and row strides. Thus a valid vector start always admits the complete 32-byte copy, including tail iterations. Copy width, `_vector` implementation and Int64 row-address products are unchanged. No cross-warp exchange or barrier is required.
- **SF padding:** every row visits every four-byte scale group once, using the same canonical Int64 offset. Valid routes copy the original source word. Invalid routes and the suffix through `ceil(active_rows /128) *128` are zeroed. Invalid payload and SF allocation beyond that extent remain untouched. This is the current 0def contract; the older N16 extra 16-row contract no longer applies.
- **Empty routes:** active count zero with positive allocated capacity performs no payload/SF writes. Every CTA still reaches the PDL startup block before the empty row loop. A truly zero allocated capacity produces grid 0 in both baseline and candidate; this is an existing boundary and is not claimed covered or fixed here.
- **PDL:** the wait, CTA0 release and first-warp launch trigger are AST-identical, before row ownership or validity divergence. Reducing the CTA count does not remove a participating CTA’s trigger. This source check does not independently validate a live predecessor chain.
- **Generality:** scheduling depends only on row capacity, width and hardware thread capacity. No dtype/model/tile threshold was added. The byte-copy path continues to accept packed FP4, E4M3 and E5M2 raw payloads with supported SF16/SF32 geometry. The complete MoE API supports a subset of those raw combinations; the gate explicitly distinguishes them. Per-token scale arithmetic is outside preparation and unchanged.

The historical `scripts/prep_linear_sf_experiment/probe_exact.py` was reused as a local adapted helper, with provenance in `gate-adaptation.json`. The adaptation corrects its stale N16 padding oracle, pins 0def, uses actual MXFP8 E4M3/SF32 in the smoke suite and appends one minimal-width case whose capacity exceeds the device-derived persistent grid cap. It would run seven specializations and 42 full-byte guarded CUDA graph checks, including poisoned padding/mappings, zero and changing route counts, original-token selection, and source/metadata immutability. The historical helper and evidence were preserved. No upstream tests were added.

`probe_exact.py`, `run_gate.py` and `audit_static.py` pass Python compilation; source `git diff --check` passes. The runner refuses a busy GPU, verifies source/native cache identity, uses a fresh source-private CuTe namespace, and caps execution at 300 seconds. Helpers were staged on c3 without launching GPU work.

**Disposition:** root’s first whole-chain screen showed regressions and requested closing this static review. The focused GPU byte gate was deliberately not run; no candidate GPU correctness, sanitizer or performance claim is made by this audit. Keep the local helper for a future justified preparation change.
