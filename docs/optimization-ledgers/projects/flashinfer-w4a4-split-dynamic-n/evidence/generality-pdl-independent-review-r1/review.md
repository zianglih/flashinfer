# Generalized PDL and quantizer publication review

Reviewed combined integration snapshot `generality-planner-cleanup-r2/source.json` (patch815e433e, coref3170f36) and isolated quantizer snapshot `generality-quantizer-publish-r2/source.json` (patch8ac61640, quantizer450fd2b). Read-only source review; this is not an additional runtime gate.

## Finding

The newly added narrow two-CTA SF readiness handoff needs explicit cluster scope. The code calls `cute.arch.mbarrier_arrive(ready, 0)` without scope; the recorded installed SDK implementation defaults remote arrivals to CTA scope and explicitly distinguishes DSMEM data handoffs. Each CTA first waits for its own cp.async completion, then the leader waits for the combined signal before group-2 S2T reads both CTAs' SF storage. This is a cross-CTA data visibility dependency, so completion counts alone are insufficient as the formal ordering proof. The core agent confirmed the concern and owns the explicit arrival/wait scope correction and generated-code check. It is separate from the isolated quantizer change.

## PDL ordering and ownership

- CUDA13.2 PTX9.2 griddepcontrol semantics establish a same-memory-domain dependency-start edge from a GPU release before the first CTA trigger. All relevant current paths still execute the dependency wait; it makes prerequisite writes available before any dependent payload access. [PTX9.2 griddepcontrol](https://docs.nvidia.com/cuda/archive/13.2.0/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-griddepcontrol)
- Preparation waits for the routing ancestor, then only warp0 release-publishes and triggers. It does not claim its own payload/SF stores are ready. FC1 early loads touch only immutable `num_tiles`, `expert_idx`, weights and weight scales. Its all-thread wait still precedes B/SFB and output-scale/token payload reads.
- FC1 likewise waits before its sole warp0 release+trigger. The per-token quantizer's three mutually exclusive paths all use warp0 fence+trigger after their common wait, so another warp cannot issue the first unfenced trigger. Its `acq_rel.gpu` fence is stronger than the release edge needed for relaying ancestors, but remains correct. SF layout conversion after quantization is only a view/permute, with no intervening device launch.
- CLC startup and the scheduler publication use the same initial work object and mapping: `route * total_m_tiles + tile_x // cta_group_size`. The installed scheduler adds each CTA's cluster rank to tile_x, so integer division maps both CTAs to the same logical tile. Padded initial routes skip preload; they are also skipped by queue publication. A later cancellation cannot return the already executing initial tile.
- Startup primes `min(num_stages,k_tiles)` stages starting at producer index0/phase1. The main producer starts at the same state and skips exactly that initial tile's primed K prefix. B and TMA-SFB complete the already acquired expected byte count after the wait. Other tiles acquire normally. No-work paths still wait and perform the original independent ring drains.
- Both CTA warp0s issue their local A/SFA/B copies. `PipelineTmaUmma.producer_acquire` waits on each local empty ring but only the leader establishes the full transaction expectation; that count includes both CTAs. Group-2 TMA completion targets the leader barrier, while UMMA release signals both empty slots. The startup split does not add a second expect-tx or alter this ownership. Narrow cp.async SFB remains outside that TMA byte count and needs the separate cluster readiness correction above.

## Small performance opportunity (not implemented)

The quantizer can move a single warp0 release+trigger to immediately after its common dependency wait, deleting its three later trigger sites. Its downstream early work only needs completed ancestors/independent weights; it still waits before quantized payload, SF and token scales. This would also give the non-register-resident branch useful startup overlap, instead of triggering after all quantization stores. Test as a separate change: earlier weight prefetch can compete with the quantizer's input reads for L2/DRAM, so correctness does not imply a gain. No model/dtype/tile gate is needed. A narrower release-only fence may simplify semantics but is not a measured performance claim.

The review found no additional PDL mapping, first-stage accounting, no-work or quantizer first-trigger blocker. That conclusion does not validate the combined candidate's still-pending narrow-CTA execution/codegen gate.
