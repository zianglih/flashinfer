# NVFP4 W4A16 stored layout and online TMEM transform

Read-only source audit, 2026-10-08. Current FlashInfer main pinned to `bcfa6539db86bf1202bb1a0fb2fcb15aaf1b36a4`. Relevant source snapshots are in `evidence/weight-layout-current/`. No kernel execution performed.

## Conclusion

W4A16 reuses the W4A4 prepared weight and block-scale layout **within each implementation**. The split CuTe DSL and MegaMoE implementations do not use one identical global row order. Split uses alternating **up64/gate64** blocks; MegaMoE uses alternating **gate16/up16** blocks. Both preserve the W4A4 layout of the corresponding backend.

The split kernel adapts the common stored NVFP4 layout to BF16 MMA while loading/dequantizing a tile and writing the transformed operand to TMEM. It composes a different SMEM *view* for both packed weights and block scales, so it can read the matching up16/gate16 slices and store decoded BF16 values into one 32-row TMEM band. This is part of the existing weight-decode pipeline, not a separate global-memory weight-repacking pass. MegaMoE's shared gate16/up16 storage order already matches each warp's band, so it decodes directly into BF16 operand-A TMEM without that extra row-view permutation.

[Same preparation branch](https://github.com/flashinfer-ai/flashinfer/blob/bcfa6539db86bf1202bb1a0fb2fcb15aaf1b36a4/flashinfer/fused_moe/prepare.py#L2542-L2588) applies `_interleave_linear_and_gate(..., group_size=64, dim=1)`, quantizes the common tensor and converts the block-scale layout. `_interleave_linear_and_gate` is [lines 2482–2492](https://github.com/flashinfer-ai/flashinfer/blob/bcfa6539db86bf1202bb1a0fb2fcb15aaf1b36a4/flashinfer/fused_moe/prepare.py#L2482-L2492); it transposes the half-vs-group axes, creating alternating 64-row blocks. Canonical split FC1 is `[up, gate]` as documented in the same file's weight conventions and reflected in the split epilogue.
- [Packed weights and scales enter SMEM; view remap](https://github.com/flashinfer-ai/flashinfer/blob/bcfa6539db86bf1202bb1a0fb2fcb15aaf1b36a4/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py#L1048-L1074). The gated remap is `cute.make_layout(((16, 2), 4), stride=((1, 64), 16))`, applied identically to `sA_input` and `sS_input`. It maps destination rows 0:32 to source rows 0:16 and 64:80, rows 32:64 to 16:32 and 80:96, etc. Thus each 32-row band contains both up/gate slices for 16 logical features. `cute.composition` changes the access mapping; it does not move the raw SMEM payload.
- [Partition decoded destination as the MMA A-fragment](https://github.com/flashinfer-ai/flashinfer/blob/bcfa6539db86bf1202bb1a0fb2fcb15aaf1b36a4/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py#L325-L348): destination starts after accumulator TMEM and is viewed with `tiled_mma.make_fragment_A(...).layout`. This distinguishes decoded weight storage from FP32 accumulator storage.
- [Load, decode, then store transformed A](https://github.com/flashinfer-ai/flashinfer/blob/bcfa6539db86bf1202bb1a0fb2fcb15aaf1b36a4/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py#L525-L575). `cute.autovec_copy` reads packed weights plus scales through the transformed views. `decode_nvfp4_fragment_to_bf16` returns BF16 register fragments. `mixed_input_utils.store_transformed_a` writes them to the operand-A destination. [TMEM copy atom](https://github.com/flashinfer-ai/flashinfer/blob/bcfa6539db86bf1202bb1a0fb2fcb15aaf1b36a4/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py#L1157-L1169) uses `tcgen05.St32x32bOp(Repetition(8), Unpack.NONE)`.
- [BF16 MMA consumes the same TMEM operand-A view](https://github.com/flashinfer-ai/flashinfer/blob/bcfa6539db86bf1202bb1a0fb2fcb15aaf1b36a4/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py#L1680-L1694).
- [Epilogue loads matching halves, scales FP32 accumulators](https://github.com/flashinfer-ai/flashinfer/blob/bcfa6539db86bf1202bb1a0fb2fcb15aaf1b36a4/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py#L1984-L2021): `up` and `gate` come from the two halves of the same gated accumulator fragment; both are multiplied by the FP32 expert alpha before SwiGLU. This does not require a global intermediate holding separate gate and up outputs.

## Suggested blog wording

> The weights themselves keep exactly the same prepared NVFP4 layout as our W4A4 kernel, including the interleaved FC1 rows and their block scales. We adapt the layout inside the weight-decode pipeline. For the split kernel, each 64-row up/gate block is read as matching 16-row slices; after local E2M1×E4M3 decoding, the BF16 fragments are written into the tensor-core operand's TMEM layout. This places each up/gate pair inside the same warp's 32-row TMEM band, so the epilogue can load both FP32 accumulators, apply the global scale, and compute SwiGLU together. No separate weight repack or gate/up intermediate is needed for W4A16.

> MegaMoE preserves the same principle with its own W4A4 layout: the prepared weights already alternate gate16/up16 blocks, so those pairs decode directly into the matching TMEM bands.

Editorial precision: call it the **same layout as the corresponding W4A4 kernel** if discussing split and MegaMoE together. Do not say all backends use gate16/up16 in HBM, or that the split view permutation runs in MegaMoE too. The physical TMEM store materializes the BF16 MMA layout, whereas the preceding SMEM composition is only an addressing view. Prefer “load FP32 accumulators from TMEM and scale them in the epilogue” to a claim that FP32 scaling happens directly inside TMEM memory.
