# K3 secondary tactic probes

Source-only review, 2026-10-08. These are **unmeasured existing-knob probes**, not catalog recommendations or evidence that a bottleneck is exposed. No GPU calls, correctness runs, or repository changes were made for this review. The common control is M256/N64/K256, C2, G1024, F4, scheduler depth2, epilogue flags `(2,4)`, epilogue return, and no fused FC2/TMA reduction. Keep PDL and the deterministic integrated combine enabled in the benchmark.

## Publication batching: source-level safety and actual effect

The existing tracker assigns a pending counter address to a lane, flushes when the batch fills **or the next work phase differs**, and ends with a final flush. Every non-null pending lane executes its own `red.release.gpu.global.add.s32`. A larger batch can group instruction issue but does not coalesce increments into fewer atomics. The reviewed `(4,4)`, `(2,8)`, and `(4,8)` thresholds fit within the existing32-lane pending-address capacity. [Tracker](flashinfer/flashinfer/moe_ep/kernel_src/sm100/cutedsl_megamoe/src/src/flag_batch.py:45); [epilogue threshold setup](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/epilogue.py:66).

The epilogue finishes the work, consumes the next scheduler descriptor, rendezvouses its store warps, and then publishes the completed work. Thus a phase change flushes FC1 publications before waiting on the next phase's accumulator. Scheduler descriptor production does not wait for those publications: readiness is a `peek_only=True` load-and-compare, and the actual activation wait is downstream. Increasing the threshold does not add a new circular dependency in this source path. It may delay readiness or alter compiled scheduling; GPU compilation and correctness remain unqualified. [Epilogue loop](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/epilogue.py:144); [nonblocking peeks](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/custom_ext.py:235).

For `token_back_mode="epi_warps"`, `signal_fc2_done` gives the tracker a null address with `no_fire=True`. Consequently `(4,8)` versus `(4,4)` in that mode does **not** test delayed FC2 release publication; it only changes no-op bookkeeping/codegen. `(4,4)` is the clear FC1 probe there. To study FC2 batching, use `reuse_dispatch_warps` and compare `(2,8)` to `(2,4)` first, then `(4,8)` to `(4,4)`. The current store fence and rendezvous stay intact. [FC2 publication branch](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/epilogue.py:221).

## Does scanning 112 experts explain exposed scheduler overhead?

**It is a plausible source-level cost, not an established bottleneck.** There are two distinct costs:

1. Each new group runs a greedy sequential pass over expert counts to establish the FC1/FC2 work ranges. Zero-token experts still require metadata traversal. It then primes the current expert. A larger group can require a longer first pass before any descriptor is ready.
2. Each persistent cluster retains a monotonic expert cursor as its atomically claimed work IDs advance. It walks skipped experts to reach the selected interval; switching to FC2 rewinds to the group start. It does **not** scan all112 experts for every work tile. Each later claim also has its existing atomic/shuffle/DSMEM broadcast handshake. [Greedy group setup](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/fc1_fc2_fuse_sched.py:730); [expert cursor](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/fc1_fc2_fuse_sched.py:659); [work decoding](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/fc1_fc2_fuse_sched.py:914); [claim protocol](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/fc1_fc2_fuse_sched.py:565).

This is a CPU model of the source's threshold, not timing, dynamic scheduling, or a count of all scheduler metadata loads. The [full model and source hash](evidence/tactics/secondary/routing-group-model.json) are preserved.

At T4, all budgets≥512 already have one group and scan all112 expert slots before producing the first work. G2048/G4096 cannot improve that group structure. At T512, G4096 reduces three groups to one but lengthens the first greedy pass43→112; G256 does the opposite. This makes the small-budget controls meaningful even if large budgets are flat.

S3 can buffer a later traversal burst, but cannot eliminate initial scanning, repeated cursor maintenance, atomic claims, or a downstream blocked activation loader. Its added record/barriers require48 bytes before allocator alignment, potentially128 bytes after alignment; inspect actual K3 fitted raw/activation stages rather than reusing old H7168 resource counts. [Stage fitting](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/megamoe_kernel.py:410); [prior resource derivation](../hashinfer-w4a16-megamoe/ep4-perf-20260920/PIPELINE_RESOURCE_AUDIT.md#existing-pipeline-and-s3-mechanism).

If the fixed S3/G probes remain flat, the source alone does not justify rewriting expert scans. Useful later evidence would distinguish time spent selecting/publishing a descriptor from consumer starvation on that descriptor, and separate startup from steady state. Existing trace range `scheduler_select_next_work_tile` and consumer wait ranges can support that investigation; recorded profiling time should not replace native CUPTI performance results.

## Geometry control detail

For a one-token-block expert, M256/C2 contributes24 FC1 cluster work tiles and14 FC2 tiles in K3. M128/C1 contributes48 and28. Therefore M128/G2048 and M256/G1024 have exactly matching greedy expert boundaries for the same routes, while M128/G1024 packs roughly half as many active experts per group. Use both JSONs if pursuing M128; comparing only the G1024 arm confounds the grouping change with the smaller independent-CTA geometry. ## Deeper direction: an allocated N32 token tile

**N32 is unsupported by the present implementation, not merely omitted from AUTO. The inspected source does not suggest an inherent 32-token BF16 MMA limitation.** Current N64/N128 allocations already emit a runtime MMA descriptor using `align16(valid_tokens)`, so a nonempty tile with1–16 routed tokens issues N16, and17–32 tokens issues N32. The allocated tile controls staging, accumulator storage, scheduling, and epilogue work; it is not the number of columns always computed by the tensor core. [Runtime descriptor and K16 issue loop](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/dynamic_mainloop.py:111).

This is particularly relevant to the saved K3 decode sweep: every expert has at most23 tokens at globalT512, and smaller decode rows are also below32. Moving those rows from allocated N64 to N32 would leave the issued MMA widths and number of expert/token work blocks unchanged. It would not halve tensor-core arithmetic, weight TMA bytes, or the two-WG dequantization work. Its potential benefit is a smaller static epilogue and activation staging footprint, with no runtime empty-half branch; its potential cost is compiler/layout complexity and different pipeline scheduling. The currently tested halfguard is informative but is not the same change as a fully static N32 path.

### Dequantization and TMEM budget

The existing raw A/SF tile is feature×K, independent of token width. M256/C2 and M128/C1 each own128 feature rows per CTA; K remains256. The shared split-kernel decoder still partitions the same128×256 packed-weight tile between two transform warpgroups and writes the same128-column BF16 decoded-weight stage. Decreasing N does not give either decoder less arithmetic. Its decoded-TMEM base moves after the smaller accumulator allocation; the load/store partition and alignment must still be checked against the actual compiler. [Inherited CTA geometry](flashinfer/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py:201); [two-WG transform partition](flashinfer/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py:348).

Under the current capacity formula, N64 uses `2×64 + 3×128 = 512` TMEM columns. N32 would use `2×32 + 3×128 = 448`, which still rounds to a512-column allocation. The64 freed columns cannot fit a fourth128-column decoded stage. It would not increase decoded-stage count or resident-CTA concurrency by itself. BF16 activation SMEM per stage could halve; whether that changes fitted raw stages must be inspected rather than assumed, and `_fit_raw_stages` already caps the raw search at5. [TMEM formula](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/megamoe_kernel.py:90); [allocation rounding](flashinfer/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py:262); [stage fitting](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/megamoe_kernel.py:410).

For prefill, N32 can create more token blocks and reload/redecode the same expert weights for each one. Therefore any implementation should first be scoped to the sparse decode regime; do not infer a useful prefill tactic from the smaller allocation. A minimal source design would preserve the current two-WG decoder and two accumulator stages, specialize both epilogues for one32-token half, and keep N64/N128 intact. This is substantially deeper than the current existing-knob queue, and no candidate patch is proposed by this audit.

### M128/C1: weight redundancy versus cooperative activation reads

**M128/C1 does not inherently double global weight traffic versus M256/C2.** M256/C2 covers256 feature rows per cluster by assigning128 distinct rows to each of its two CTAs. M128/C1 covers128 rows in one CTA; two independent claims cover the same256 rows. For the same expert/token block, both visit each packed weight/SF feature slice once. The number of cluster claims doubles, but the total CTA feature work and weight-decode work remain the same. This distinction follows the inherited `cta_tile_shape_mnk = (M / cta_group_size, N, K)`, per-CTA `partition_A`, and `work.tile_m_idx / cta_group_size` tile addressing. [CTA shape](flashinfer/flashinfer/fused_moe/cute_dsl/blackwell/moe_w4a16_kernel.py:201); [weight partition and tile index](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/megamoe_kernel.py:908).

The repeated operand is **activation B**. A two-CTA MMA splits the token operand between its participants and consumes that cooperative operand for256 feature rows; one-CTA M128 needs the complete token operand for each128-row tile. Thus, in the static N64/K256 layout, the two-CTA pair stages a total64×256 BF16 activation elements, while two independent M128 CTAs stage2×64×256. This is a source-level TMA payload comparison, not a claim that DRAM traffic doubles: cache reuse, out-of-bounds fill, and dynamic non-leader shifts affect observed memory traffic. Calling this simply “loss of multicast” is imprecise; the important difference is the loss of the two-CTA cooperative B operand. [Activation partition and dynamic shift](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/megamoe_kernel.py:987); [B transaction accounting](flashinfer/flashinfer/moe_ep/cute_dsl/megamoe/bf16_nvfp4/megamoe_kernel.py:840).

M128/C1 also changes `tcgen05.mma.cta_group::2` to`::1`, removes the second-CTA MMA participation, gives each CTA an independent scheduler stream, and doubles global work claims. Both retain640 threads, two decoder WGs, and128 feature rows per CTA. It is a scheduling/cooperation tradeoff, not a smaller per-CTA dequant tile or a weight-byte-saving tactic. There is no D/E feature-padding win for K3. The grouping-unit correction in the preceding section remains necessary.

For the saved T4 routes, each rank has3–15 active experts and at most360 FC1 cluster tiles. Both budgets exceed that total; both first greedy passes visit all112 expert slots and terminate by expert exhaustion. Thus neither fewer group transitions nor a shorter first scan explains their difference on this fixture. Equal group boundaries establish the same abstract task ordering; atomic claim interleaving across persistent clusters can still differ with execution timing.

The hint remains a compile-time constant, so the compiler sees a different literal in the first and subsequent group-threshold expressions and a different named specialization. Instruction scheduling, register assignment, instruction placement, or other generated-code details can differ even when the runtime groups coincide. However, there is no source evidence that4096 specifically triggers beneficial constant folding. Expert counts are raw runtime loads with no scheduler-visible T4 bound; the source does not prove the whole layer fits one group and replace the scan with a constant result. [Count load](flashinfer/flashinfer/moe_ep/kernel_src/sm100/cutedsl_megamoe/src/moe_nvfp4_swapab/moe_utils.py:364).

A source audit therefore cannot assign the preliminary gap to the scheduler or to codegen. The useful sequence is the pending native A3 bracket, repeat any gain with all knobs and source fixed, then compare the actual generated PTX/SASS and resources if a same-group difference survives. Distinguish a threshold-literal-only binary difference from changes elsewhere in the kernel, and preserve cold-cache/rank timing boundaries. Fresh allocation addresses and run-to-run readiness are additional uncontrolled possibilities until checked; they are not identified causes. The earlier [group-hint source audit](../hashinfer-w4a16-megamoe/ep4-perf-20260920/GROUP_HINT_SOURCE_AUDIT.md) reached the same distinction between equivalent group structure and unproven instruction identity.
